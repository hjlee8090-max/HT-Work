# 00 — 오케스트레이터 · ticket-pilot 구축 실행 세트 v0.6-exec

> 원본: ticket-pilot-구축계획서-v0.6.md (설계 기록으로 동결, 갱신하지 않음)
> **이 폴더가 구축 실행의 기준 문서다.** 구축 중 설계 변경이 승인되면 이 폴더의 해당 파일을 고치고 아래 변경 이력에 기록한다.

---

## 1. 모델 역할과 런타임 자족성 [확정]

- **구축 모델 (이 문서들의 독자): Claude Fable 5** — Claude Code에서 Phase 파일을 순서대로 실행해 플러그인을 만든다.
- **런타임 모델 (배포물의 독자): Claude Opus 4.8** — 플러그인 사용 시점에는 SKILL.md · commands · CLAUDE.md 관리 블록 · board.html만 읽는다. 이 구축 문서들은 영원히 보지 못한다.

따라서 다음 규칙이 성립한다:

1. **배포물은 구축 문서 없이 완결되어야 한다.** §4.6(프로필) · §4.7(제안 파이프라인) 같은 계약은 해당 SKILL.md 본문에 전사한다. 배포물 어디에든 "구축계획서" · "10-contracts" · "§4.7 참조" 류의 문구가 남아 있으면 결함으로 간주하고 즉시 수정한다.
2. SKILL.md와 CLAUDE.md 블록은 Opus 4.8이 **추가 맥락 없이 단독 세션에서 실행 가능한 수준**으로 쓴다. 순서: 목적 → 입력 → 실행 단계 → 완료 기준.
3. Phase 5의 E2E 검증은 가능하면 런타임 조건(Opus 4.8 세션)에서 수행하고, 불가하면 그 사실을 인수 보고에 명시한다.

## 3. 실행 규칙

1. Phase 순서대로 실행한다: 20 → 21 → 22 → 23 → 24 → 25. 각 Step의 완료 기준(DoD)을 모두 만족해야 다음 Step으로 넘어간다.
2. **스텝 시작 전, _PROGRESS.md에 해당 Step을 "진행중"으로 먼저 기록한다.** 플러그인의 in_progress 선기록과 같은 원리다 — 세션이 끊겨도 재개 지점이 남는다.
3. Phase가 끝날 때마다 산출물 경로와 검증 결과를 사용자에게 보고하고, 승인 후에만 다음 Phase 파일을 연다.
4. 이 세트에 없는 기능 · 필드 · 옵션을 추가하지 않는다. 필요하다고 판단되면 01-context.md의 Open Issues에 제안만 기록한다.
5. 상태 표기: **[확정]** 재합의 없이 변경 금지 / **[유력안]** 기본값, 변경은 사용자 확인 후 / **[가정]** 확인 권장 / **[보류]** v1 제외.
6. 커밋: Step당 1개 이상, 커밋 메시지에 Step 번호를 남긴다.
7. 세션이 끊긴 뒤 재개할 때는 _PROGRESS.md에서 "진행중" 또는 첫 "대기" Step을 찾아 그 지점부터 계속한다.
