# Ticket Pilot (`tp`)

로컬 프로젝트의 LLM 작업을 **티켓 단위로 계획 → 승인 → 실행 → 보고**하고, 일 단위 메모리 3계층으로 세션 간 맥락을 유지하는 Claude Code / Cowork 플러그인.

핵심 가치 3가지:
- **통제** — 사용자가 승인한 티켓만 실행된다. 같은 티켓을 두 번 실행하지 않는다.
- **승인이 곧 시작** — 채팅으로 "T-001 승인해줘"라고 하면 승인과 동시에 실행까지 이어진다. 승인·실행을 두 번 요청할 필요가 없다 (승인만 하려면 "승인만 해줘").
- **연속성** — `/tp:done` 한 번으로 하루가 기록되고, 오래된 기록은 자동 압축되어 다음 세션의 맥락이 된다.

## 설치

세 가지 경로 중 하나를 쓴다.

**1) GitHub 마켓플레이스**

```
/plugin marketplace add hjlee8090-max/HT-Work
/plugin install tp@ht-work
```

**2) 로컬 마켓플레이스** (저장소를 받아 둔 경우)

```
/plugin marketplace add <클론 경로>/ticket-pilot
/plugin install tp@ticket-pilot
```

**3) Cowork 커스텀 플러그인 업로드** — `ticket-pilot/` 폴더를 압축해 Cowork의 플러그인 업로드 메뉴로 올린다.

설치 시 커맨드 네임스페이스는 `/tp:*`다. 다른 플러그인과 `tp` 이름이 충돌하면 설치 단계에서 확인하라.

## 사용법 — 커맨드 5개

| 커맨드 | 하는 일 | 자연어 트리거 예 |
|--------|---------|------------------|
| `/tp:init` | 프로젝트 스캔 · 기존 스킬 인벤토리 · 목적 인터뷰 → CLAUDE.md 블록 + `.ticket-pilot/` 워크스페이스 생성 | "프로젝트 세팅해줘" |
| `/tp:tickets` | 티켓 초안 생성 + 근거 있는 연계 제안(최대 3건) + 보드 재생성. 보드에서 복사한 변경 JSON 반영도 담당. **채팅 승인은 그 자리에서 실행까지 인계** | "티켓 만들어줘", "보드 변경 반영해줘", "T-001 승인해줘" |
| `/tp:run` | 승인된 티켓을 우선순위·의존성 순으로 실행(독립업무는 서브에이전트 병렬), 증빙 수집, 완료 후 후속 제안·blocked 요약 | "티켓 확인해줘", "티켓 실행해줘", "후속 제안 정리해줘" |
| `/tp:done` | 하루 마감 — 오늘 기록, 메모리 3계층 압축, 프로필 규칙 승격 보고, 소통 규칙 CLAUDE.md 동기화, 반복 패턴 스킬 제안 | "오늘 마감해줘", (압축만) "메모리 정리해줘" |
| `/tp:handoff` | 세션 인계 — 중간 정리(HANDOFF.md 저장) + 다음 세션 재개 프롬프트 제공. 메모리·프로필은 건드리지 않음 | "핸드오프", "중간 정리해줘", "세션 넘겨줘" |

기본 루프: `init`(최초 1회) → `tickets` → **승인** → 실행 → `done`. 승인 경로는 둘이다 — **board.html에서 승인**하면 `run`으로 실행하고, **채팅으로 "T-001 승인해줘"**라고 하면 그 자리에서 실행까지 이어진다.
세션이 불안정해지면 언제든 `handoff`로 중간 정리하고, 새 세션에 재개 프롬프트를 붙여넣어 이어간다.

## 보드(board.html) 저장 방식 — 브라우저별 안내

`.ticket-pilot/board.html`을 브라우저로 열어 티켓을 승인·반려·편집하고, 카드 모달에서 실행 시 반영될 **코멘트**(예: "이거 할 때 ○○ 참고해줘")를 남긴다. 카드를 끌어 **초안 ↔ 승인** 컬럼 사이로 옮기는 드래그 상태 전환도 된다.

- **크롬·엣지 등 크로미움 계열 (권장 — 파일 직접 저장)**: 최초 1회 [tickets.json 연결] 버튼으로 `.ticket-pilot/tickets.json`을 선택해 두면, 이후 [저장] 버튼이 보드의 변경(승인·반려·편집·코멘트)을 **tickets.json에 바로 덮어쓴다**. 저장한 상태는 보드를 다시 열 때마다 그대로 보인다 — 보드가 연결된 파일을 먼저 읽기 때문이다(연결 정보는 브라우저에 보관되며, 재방문 시 권한 확인이 뜨면 1클릭으로 허용. 크롬 122+에서 "모든 방문에서 허용"을 선택하면 그 클릭도 사라진다). 클로드에게 되붙여넣을 필요가 없다 — 클로드는 tickets.json을 읽고 바로 작업한다.
- **사파리·파이어폭스 (클립보드 경로)**: 파일 직접 저장 API가 없어 [프롬프트 복사(코워크)] 버튼을 쓴다 → 변경된 티켓 JSON이 클립보드에 복사된다 → 클로드 채팅에 붙여넣고 "보드 변경 반영해줘"라고 입력하면 검증 후 tickets.json에 반영된다.
- 채팅으로 "T-001 승인해줘", "T-003에 코멘트: ○○ 참고해서 진행해줘"라고 말해도 같은 검증을 거쳐 반영된다. **채팅 승인은 반영에서 멈추지 않고 곧바로 실행까지 간다** (아래 절).
- 보드를 연 뒤 에이전트가 tickets.json을 바꾼 상태에서 [저장]을 누르면 충돌 안내가 뜬다 — [파일 다시 불러오기] 또는 [그래도 저장]을 선택한다.
- 진행중(in_progress)·완료(done)·보류(blocked) 카드는 읽기 전용이다 — 드래그·모달 액션 모두 막혀 있고, 실행 상태는 에이전트만 기록한다. 진행중·완료 컬럼으로의 드롭도 불가능하다.

## 채팅 승인 = 즉시 실행

채팅에서 승인하면 **승인 상태 변경과 실행이 한 번에** 일어난다. "승인해줘" → 보고 → "실행해줘"로 두 번 나눠 요청하지 않아도 된다.

| 발화 | 일어나는 일 |
|------|-------------|
| "T-001 승인해줘" | approved로 바꾸고 **곧바로 실행** — 승인 반영과 실행 결과가 한 보고로 온다 |
| "T-001·T-002 승인", "초안 전부 승인" | 승인한 티켓들을 실행 프로토콜에 태운다 (독립업무 묶음이면 병렬, 아니면 우선순위 순 직렬) |
| "T-007 재승인해줘" (보류 티켓) | blocked → approved로 되돌리고 다시 실행한다 |
| "T-005 재오픈해줘" (완료 티켓) | done → approved로 되돌리고 다시 실행한다 |
| "T-001 승인만 해줘", "실행은 나중에" | 상태만 바꾼다 — 이후 "티켓 실행해줘"로 이어서 실행한다 |
| board.html에서 승인 후 [저장] | 상태만 바뀐다 — 실행은 `/tp:run`으로 시작한다 (보드는 승인 화면이지 실행 지시가 아니다) |

승인이 실행으로 이어져도 통제는 그대로다:

- **실행 범위는 이번에 승인한 티켓까지다.** 예전에 승인만 해 두고 안 돌린 티켓이 덩달아 실행되지 않는다 ("승인하고 밀린 것까지 다 실행해줘"라고 하면 포함된다).
- **의존성은 지켜진다.** 승인한 티켓이 아직 끝나지 않은 선행 티켓을 기다려야 하면 실행하지 않고, 무엇을 기다리는지 보고한다. 자격을 만들려고 선행 티켓을 임의로 승인하지 않는다.
- **실행 경로를 우회하지 않는다.** 승인 즉시 실행도 `/tp:run`과 똑같이 중복 방지 선점 기록 → scope 검증 → 증빙 수집을 거친다.
- **반대 방향은 성립하지 않는다.** 초안 티켓에 "실행해줘"라고 하면 바로 실행하지 않고 "승인하고 바로 실행할까요?"라고 한 번 묻는다 — 승인 없이 실행되는 경로는 없다.

## 티켓 코멘트 — 티켓에 직접 요청 남기기

티켓 카드를 클릭하면 상세 모달 **우측에 "요청·코멘트" 패널**이 있다 (넓은 입력칸 — 여러 줄 긴 요청도 그대로. 좁은 화면에서는 내용 아래로 내려온다). 여기에 "할 때 docs/스타일가이드.md 참고해줘", "○○ 방식으로 처리해줘" 같은 지시를 남기면:

- 코멘트는 tickets.json의 해당 티켓 `comments` 필드에 저장된다 (초안·승인·반려 상태에서만 추가·삭제 가능).
- `/tp:run` 실행 시 에이전트가 **steps 수행 전에 코멘트를 읽고 지시로 반영**하며, 반영 내역을 결과 요약에 남긴다.
- 코멘트가 티켓 내용과 모순되면 실행하지 않고 보류(blocked) 처리 후 충돌 내용을 보고한다.
- 코멘트는 사용자 전용 공간이다 — 에이전트가 임의로 쓰거나 지우지 않는다.

## 독립업무 병렬 실행 — 서브에이전트

서로 결과를 기다릴 필요가 없는 티켓들은 `/tp:run`이 **서브에이전트(tp-worker)로 병렬 실행**한다.

- **독립 판정은 선언 기반**: 티켓의 `scope`(수정할 파일·디렉터리)가 서로 겹치지 않고 상호 의존이 없는 approved 티켓만 한 배치(최대 3건)로 묶인다. scope를 비워 두면 그 티켓은 안전하게 직렬로만 실행된다.
- **수렴 티켓**: 병렬 묶음이 최종적으로 하나의 작업(통합·조립·통합 검증)으로 이어지면, 티켓 생성 시 수렴 티켓이 함께 만들어져 `depends_on`으로 연결된다 — 묶음이 전부 done이 되면 자동으로 실행 자격을 얻는다.
- **기록 주체는 하나**: 워커는 프로젝트 파일 작업만 하고 보고(JSON)만 반환한다. tickets.json·보드 갱신은 항상 오케스트레이터가 한다. 워커 보고는 그대로 믿지 않고 검증한다 — 변경 파일이 scope를 벗어나면 done이 아니라 blocked로 기록된다.
- **재량(latitude)**: 서브에이전트는 맥락을 모르므로 기본은 `엄격`(steps 외 작업 금지, 발견 사항은 보고만)이다. "이 티켓은 알아서 개선해도 돼"라고 명시하거나 보드 편집에서 `유연`으로 바꾼 티켓만 scope 안 부수 개선이 허용되고, 그 내역은 결과에 "재량:"으로 구분 기록된다.
- 서브에이전트 도구가 없는 환경에서는 자동으로 기존 직렬 실행으로 동작한다.

## 수정 티켓 — 완료된 작업에 대한 수정 요청

완료(done) 티켓이 만든 산출물에 오류·변경 요청이 생기면, 플러그인은 그 자리에서 고치지 않고 **수정 티켓**을 만들어 승인 흐름을 태운다 (`rework_of`로 원 티켓과 연결):

- 원 티켓의 결과·증빙은 그대로 남는다 (역사 기록) — 무엇을 왜 다시 했는지가 티켓 체인(T-005 ← T-013 ← …)으로 남는다.
- 수정 티켓은 원 티켓의 변경 파일에서 scope를 시작하고, 검증에 **회귀 확인**(원 티켓의 기존 검증 재통과)을 포함한다.
- 보드: 수정 티켓 카드에 "↩ T-005" 배지, 원 티켓 모달에 수정 이력(어떤 수정 티켓이 어떤 상태인지)이 표시된다. 편집 폼에서 수정 대상을 지정·해제할 수도 있다.
- 같은 원 티켓의 수정이 3번째면 "원 스펙·설계 재검토를 권합니다" 알림 1줄이 붙는다 (자동 조치 없음).
- 재오픈(done→approved)은 완료 기록 자체가 틀렸을 때만 쓰는 예외 경로다.

## 세션 인계 (handoff) — 불안정한 세션을 다음 세션으로

세션이 느려지거나 맥락이 흔들릴 때 `/tp:handoff`(또는 "중간 정리해줘")를 부르면:

1. **인계장 저장이 최우선** — `.ticket-pilot/HANDOFF.md`에 하던 일(티켓 단계 체크리스트), 대화로 결정됐지만 파일에 반영 안 된 것, 사용자 답변 대기, 다음 행동, 작업 트리 상태를 기록한다. tickets.json·메모리·프로필은 건드리지 않는다 (하루 마감이 아니라 **중간 정리**다).
2. **재개 프롬프트 제공** — 복사해서 새 세션 첫 메시지로 붙여넣으면 인계장을 읽고 정합성 검증(그 사이 파일 변경·이중 재개·날짜) 후 브리핑하고 이어서 진행한다. 프롬프트는 포인터+대조 요약만 담는다 — 상태의 원본은 파일이다.
3. 재개하면 인계장은 "소비됨"으로 마킹되고, 재개 없이 `/tp:done`을 하면 마감이 인계장 내용을 오늘 기록에 흡수한다. 프롬프트를 잃어버려도 안전하다 — CLAUDE.md 작업 규칙이 세션 시작 시 대기 상태 인계장을 확인하게 한다.

## 워크스페이스 구조

```
<프로젝트 루트>/
├── CLAUDE.md                  # ticket-pilot 관리 블록 (마커 안만 관리, 밖은 불가침)
└── .ticket-pilot/             # 전체가 커밋 대상 (증빙 포함)
    ├── config.json            # { "screenshot": "auto|off", "memory": {...} }
    ├── tickets.json           # ★ 티켓 데이터의 유일한 원본
    ├── board.html             # 생성된 뷰 (보드 탭 + 리포트 탭)
    ├── profile.md             # 업무 프로필 — 관찰→패턴→규칙 (근거 인용 의무)
    ├── memory/                # RECENT(7일) · MIDDLE(주 단위) · LONG(월 단위)
    └── artifacts/T-XXX/       # 실행 증빙 (스크린샷 등, 티켓당 2장·폭 1280px 이하)
```

- 개인 업무 성향이 기록되는 `profile.md`는 공유 저장소라면 노출될 수 있다 — init이 원격 감지 시 커밋 제외 여부를 물어본다.

## 학습이 걱정된다면

- 프로필 규칙은 **관찰 3회 이상·2일 이상**일 때만 승격되고, 항상 근거(날짜·티켓 ID)를 인용한다. "앞으로/항상/하지 마"가 붙은 명시 지시는 즉시 규칙화된다.
- 승격·변경은 `/tp:done` 보고에 표로 나온다. "R-xx 거부"라고 말하면 취소선으로 보존되고 자동 재승격되지 않는다.
- 소통 규칙(C-xx)은 표현·설명 방식만 담을 수 있고, CLAUDE.md의 '소통 방식' 절에만 반영된다.

## v1 제약 사항

다음은 **의도적으로 하지 않는다**: 멀티유저 협업 · 원격 동기화 · GitHub 이슈 연동 · 로컬 웹서버 구동 · 보드 드래그앤드롭 정렬(컬럼 안 순서 바꾸기 — 상태 전환 드래그는 지원) · 자동 스케줄링(cron) · 통계 대시보드 · 재량(latitude)의 프로필 기반 자동 설정(수동 설정만 — 학습 연동은 보류).

추가 전제: 실행(`/tp:run`) 세션은 동시에 1개만 연다 (동시 변경이 감지되면 실행이 중단된다). 티켓 실행은 기본 직렬이며, 독립업무 묶음(상호 의존 없음 + scope 서로소)만 서브에이전트로 병렬 실행된다 — 이때도 tickets.json 기록은 오케스트레이터 하나가 한다. 보드는 재생성 방식이라 사람이 board.html을 직접 고친 내용은 다음 재생성 때 사라진다.

## 버전

v0.8.0 — 채팅 승인 = 즉시 실행 (2026-07-30)
- 채팅으로 승인한 티켓은 상태 변경에서 멈추지 않고 같은 턴에 ticket-run으로 인계돼 실행까지 진행된다 (ticket-create B-3). 승인·실행을 두 번 요청하던 흐름 제거. 실행 범위는 이번에 승인한 티켓으로 한정되고, 실행 통제(선점 기록·의존성 자격·scope 검증·증빙)는 `/tp:run`과 동일한 경로를 그대로 탄다.
- 보류(blocked) 티켓의 채팅 재승인(blocked→approved)을 명시 요청 경로로 허용 — ticket-run이 안내하는 재개 경로가 실제로 동작한다. 보드 경로와 "승인만 해줘"는 종전대로 상태만 변경.
- 초안 티켓에 실행을 요청하면 막다른 거부 대신 "승인하고 바로 실행할까요?"를 한 번 묻는다 (승인 없는 실행은 여전히 없음).
- tickets.json 스키마·보드 무변경.

v0.7.0 — 수정 티켓 (2026-07-24)
- rework_of 필드 추가(schema 3→4, 무손실 승격): 완료 티켓 산출물에 대한 오류·변경 요청은 즉석 수정 대신 수정 티켓으로 상시 티켓화. 원 result·증빙 불변, scope는 원 티켓 변경 파일에서 시작, 검증에 회귀 확인 포함, 수정의 수정은 체인. 보드에 ↩ 배지·수정 대상·수정 이력 표시와 편집 지원. 동일 원 티켓 수정 3건째 재검토 알림(자동 조치 없음). 재오픈은 완료 기록 오류 시 예외 경로로 정리.

v0.6.0 — 세션 인계 /tp:handoff (2026-07-24)

v0.5.0 — 독립업무 병렬 실행 (2026-07-24)
- **독립업무 + 병렬 실행**: 티켓에 scope(수정 범위) 필드 추가(schema 2→3, 무손실 승격). 상호 의존이 없고 scope가 서로소인 approved 티켓을 최대 3건씩 tp-worker 서브에이전트로 병렬 실행. tickets.json 기록은 오케스트레이터 단독 — 워커는 보고만 반환하고, scope 이탈은 검증에서 잡혀 blocked 처리.
- **수렴 티켓**: 병렬 묶음이 이어지는 최종 작업은 생성 시점에 수렴 티켓으로 함께 만들어 depends_on으로 연결 (fan-out → fan-in).
- **재량(latitude)**: 서브에이전트 자유도 티켓 단위 설정 — 기본 엄격(steps 외 금지), 사용자 명시·보드 편집으로만 유연 전환. 프로필 연동 자동화는 보류.
- 보드: 모달에 수정 범위·재량 표시, 편집 폼에서 scope·재량 수정, 유연 티켓 카드에 "재량" 배지.

v0.4.0 — 사용자 피드백 3건 반영 (2026-07-24)
- **프로세스 분해 규칙(선행 산출물 규칙)**: 문서 기반 다단계 요청은 분석·정리 → 정의(스펙) → 구현 → 검증 순서로 티켓을 분해하고 depends_on으로 연결한다. 웹 개발이면 IA 정리 → 화면별 스펙 정의 → 화면 구현 순서가 기본 — 스펙 없는 화면 구현 티켓이 실행 선두에 오지 않는다.
