# ticket-create — 티켓 생성 · 보드 변경 반영 · 보드 재생성

## 목적

두 가지 일을 한다. 요청 내용을 보고 모드를 판별한다:
- **A. 티켓 생성**: 사용자 요청을 티켓 초안(draft)으로 만들고, 프로젝트 신호에 근거한 연계 제안(suggested)을 최대 3건 붙인다.
- **B. 보드 변경 반영**: 사용자가 board.html에서 복사해 붙여넣은 JSON(또는 채팅으로 말한 승인·반려·수정)을 검증해 tickets.json에 반영한다.

두 모드 모두 마지막에 board.html을 재생성한다.

## 입력

- `.ticket-pilot/tickets.json` — 티켓 데이터의 **유일한 원본**. 없으면 "먼저 /tp:init 을 실행하세요"라고 안내하고 중단한다.
- CLAUDE.md의 ticket-pilot 블록 (목적 · 성공 기준 SC-x)
- `.ticket-pilot/profile.md` (업무 프로필) · `.ticket-pilot/memory/RECENT_MEMORY.md` · `MIDDLE_MEMORY.md`
- 이 세션에서 사용 가능한 스킬 목록 (기존 스킬 인벤토리)

## 데이터 계약 — tickets.json

```json
{
  "schema_version": 1,
  "project": { "name": "", "goal": "" },
  "updated_at": "2026-07-23T18:00:00+09:00",
  "tickets": [
    {
      "id": "T-001",
      "title": "로그인 폼 유효성 검사 추가",
      "purpose": "사유: (계기) 한 줄\n목적: (완료 시 달성 상태) 한 줄\n효과: (그래서 무엇이 가능해지는지) 한 줄",
      "steps": ["구체 실행 단계 1", "구체 실행 단계 2", "검증: 완료 판정 방법 (필수, 항상 마지막)"],
      "status": "draft",
      "priority": 1,
      "depends_on": [],
      "origin": "user",
      "created_at": "…",
      "updated_at": "…",
      "result": null
    }
  ]
}
```

- `status`: `draft | approved | in_progress | blocked | done | rejected`
- `origin`: `user`(사용자 요청 기반) | `suggested`(플러그인 제안)
- `id`: `T-001`부터 순차 부여. 반려·완료 티켓 번호도 재사용하지 않는다 (기존 최대 번호 + 1)
- `priority`: 정수, 낮을수록 먼저 실행
- `result`: 실행 완료 시에만 채워진다 (이 스킬은 null로 만든다)
- **위 필드 외 추가 금지** (태그·담당자·예상시간 등 넣지 않는다)
- 모든 상태 변경은 tickets.json 저장을 동반한다. 저장 시 파일의 `updated_at`을 현재 시각으로 갱신한다.

## A. 티켓 생성 모드

### A-1. 컨텍스트 로드

tickets.json, CLAUDE.md 블록(목적·SC-x), profile.md, RECENT·MIDDLE 메모리를 읽는다.

### A-2. 프로필 시드 (프로필이 비어 있을 때 최초 1회)

profile.md의 규칙·패턴·관찰이 모두 "(아직 없음)"이면:
1. 프로젝트에 의사결정·스타일 지식파일(DECISION_INDEX, 스타일 가이드 등)이 있으면 그것을 프로필 시드로 참조할지 먼저 제안한다.
2. 없으면 3문항 이내로 묻는다: ① 티켓 크기 선호(잘게/크게) ② 제안 적극성(적극/보통/최소) ③ 설명 수준(용어 풀이 필요 여부).
3. 답변은 임계 없이 즉시 profile.md의 규칙으로 기록한다. 근거는 `시드 인터뷰 · 날짜`. 답이 이미 대화에 있으면 묻지 않고 그대로 기록한다.

### A-3. 사용자 요청 티켓 작성

- 티켓 1건 = **1세션 안에 완료 가능한 크기**. 넘치면 분할하고 `depends_on`으로 연결한다.
- `steps`는 하위 모델이 추가 맥락 없이 수행할 수 있게 구체적으로 쓴다. 마지막 항목은 반드시 `"검증:"`으로 시작하는 완료 판정 방법이다. 코드명·버전·정책 ID 같은 실행 디테일은 steps에 담는다 — purpose에 반복하지 않는다.
- 기존 스킬로 처리 가능한 티켓은 steps에 해당 스킬명을 명시한다 (예: "docx 스킬로 보고서 생성").
- **목적 정합 확인**: 요청이 CLAUDE.md의 목적·성공 기준과 연결되지 않으면 생성 전에 1회만 확인한다 — "목적을 갱신할까요, 목적 외 작업으로 표시하고 진행할까요?" 거부가 아니라 확인이다.
- **프로필 적용**: profile.md의 작업 규칙(R-xx)을 티켓 크기·steps 상세도·제안 선별에 적용하고, 적용한 규칙 ID를 문구에 인용한다 (예: "R-02에 따라 steps를 5개 이하로 나눴습니다").
- 모든 신규 티켓은 `draft`로 만든다. **자동 승인 금지.**

#### A-3-1. purpose 작성 규칙 — 저맥락 독자 기준

purpose는 정확히 아래 3줄로 쓴다:

```
사유: <이 작업이 필요해진 계기 — 무슨 일이 있었는지>
목적: <끝나면 무엇이 달성돼 있는지 — 완료 상태>
효과: <그래서 무엇이 가능해지거나 달라지는지>
```

원칙:
1. 한 줄에 하나만 담는다 — 나열이 필요하면 steps의 몫이다.
2. 내부 코드·버전·정책 ID(`GLOSSARY_v9.1`, `POL-DLV-070`, `R02` 등)를 넣지 않는다 — steps와 중복이자 소음이다.
3. 약어를 꼭 써야 하면 처음 등장할 때 괄호로 1회만 풀어쓴다.
4. 자체 점검: "이 3줄만 읽고, 이 프로젝트를 모르는 사람이 왜/무엇을/그래서 뭐가 좋아지는지 알 수 있는가?"
5. suggested 티켓의 출처 태그(`[S3·T-003 후속]` 등)는 별도 줄로 맨 앞에 두고, 그다음 줄부터 사유/목적/효과를 쓴다.
6. 기존(구형) 티켓은 강제로 재작성하지 않는다 — board.html이 형식 미준수 시 원문 그대로 표시한다.

나쁜 예 (한 문단에 코드·정책 ID가 뒤섞여, 프로젝트를 모르면 읽을 수 없다):
> "0722 결정 중 추가 결정이 불필요한 기계적 항목만 반영한다: AIV 식별자·GLOSSARY 최종채번(R02), 회사배송부담 폐기 정책 표기·INDEX 정리(R04), 배송건 식별=접수번호 확정(R01, 표기 세부는 개발 정의 범위 명시). R03은 T-007로 분리."

좋은 예 (같은 티켓, 재작성):

```
사유: 0722 회의에서 배송 정책 일부는 결정이 미뤄지고, 바로 반영해도 되는 항목만 남았다.
목적: 추가 논의가 필요 없는 항목(식별자 채번·폐기 정책 표기·배송건 식별 방식)만 먼저 문서에 반영한다.
효과: 확정된 부분부터 반영돼, 남은 결정(R03)이 끝나는 대로 이어서 처리할 수 있다.
```

### A-4. 연계 제안 파이프라인 (suggested 티켓)

원칙: 모든 suggested는 **프로젝트 내부의 구체 신호**에서만 나온다. 출처를 인용하지 못하거나 "왜 지금인가"에 답하지 못하는 후보는 제안하지 않는다. 일반론(테스트 추가·리팩토링·문서화 등)은 그 자체로는 출처가 아니다.

**1단계 — 후보 수집.** 출처는 아래 5개뿐이다 (근거 강도 티어순):

| 티어 | 출처 | 정의 |
|------|------|------|
| T1 | S1 메모리 미해결 | RECENT·MIDDLE의 "미해결/이슈"·"내일 후보" 중 티켓화되지 않은 항목 |
| T1 | S2 블록 해제 | blocked 티켓의 재개 조건을 만드는 선행 작업 |
| T2 | S3 후속 연쇄 | done 티켓의 result.followups |
| T3 | S4 성공 기준 갭 | CLAUDE.md 성공 기준(SC-x) 중 대응 티켓(draft/approved/in_progress/done)이 없는 항목 |
| T4 | S5 스캔 갭 | 파일 스캔에서 발견된 구체 결함 — 목적과의 연결을 명시할 수 있을 때만 |

기존 스킬 인벤토리는 출처가 아니라 **가점 요소**다: 동티어 후보 중 기존 스킬로 즉시 처리 가능한 것을 우선하고, steps에 스킬명을 명시한다.

**2단계 — 필터.** 하나라도 걸리면 탈락:
- F1 프로필 규칙: 활성 R-xx가 제외하는 계열
- F2 반려 이력: rejected 티켓과 실질적으로 같은 제안 (부활은 사용자 명시 요청 시에만)
- F3 중복: 기존 draft·approved·in_progress 티켓과 중복
- F4 크기: 1세션 초과 — 첫 단계만 잘라 제안하거나 제외
- F5 근거 결격: 출처 인용 또는 "왜 지금" 1줄을 채울 수 없는 후보

**3단계 — 랭킹.**
- 1순위: 티어 (T1 > T2 > T3 > T4)
- 동티어: 기존 스킬 가점 → 프로필 패턴(승인율 높은 계열) → 최신 신호
- 상한 3건, 동일 출처 최대 2건
- **신뢰 예산**: origin=suggested이고 결정이 끝난(승인 계열 approved·in_progress·done / 반려 rejected) 최근 10건의 승인율이 1/3 미만이면 상한을 3→1로 낮춘다. 회복 여부 보고는 day-close가 한다.

**4단계 — 근거 명시.**
- 대화 제안 시 각 후보에 3요소: ① 출처 태그와 인용(날짜·티켓 ID·파일) ② "왜 지금" 1줄 ③ 적용한 프로필 규칙 ID (없으면 생략)
- purpose는 출처 태그를 첫 줄에 쓰고, 그다음 줄부터 A-3-1의 사유/목적/효과 형식을 따른다:

  ```
  [S3·T-003 후속]
  사유: T-003 완료 후 로그인 실패 시 에러 안내가 없다는 후속 이슈가 남았다.
  목적: 로그인 실패 케이스에 사용자 안내 메시지를 추가한다.
  효과: 실패 원인을 몰라 반복 시도하던 문의가 줄어든다.
  ```
- suggested도 전부 `draft`로 기록한다.

### A-5. 저장 · 보드 재생성 · 보고

1. tickets.json에 신규 티켓을 추가하고 저장한다 (updated_at 갱신).
2. 아래 "보드 재생성 절차"를 수행한다.
3. 보고: 생성 티켓 표(ID·제목·origin·priority) + suggested 각각의 3요소 근거 + "board.html을 브라우저로 열어 승인/반려(카드 클릭 또는 드래그)하고 '프롬프트 복사(코워크)' 버튼으로 복사해 붙여넣으세요. 채팅으로 'T-001 승인해줘'라고 해도 됩니다."

## B. 보드 변경 반영 모드

트리거: "보드 변경 반영해줘" + 붙여넣은 JSON, 또는 채팅 직접 지시("T-003 승인해줘", "T-002 반려").

### B-1. 검증 — 위반 항목은 사유와 함께 거부하고 반영하지 않는다

1. 붙여넣은 JSON의 `schema_version`이 현재 파일과 일치하는가 (채팅 지시는 해당 없음)
2. 변경 대상 티켓 id가 tickets.json에 존재하는가
3. **허용되는 변경은 `draft ↔ approved ↔ rejected` 간 상태 전환과 필드 편집(title·purpose·steps·priority·depends_on)뿐이다.** `in_progress`·`done`·`blocked` 카드의 변경은 거부한다 — 실행 상태는 실행 스킬만 쓴다. (예외: done 티켓의 재오픈은 사용자가 채팅에서 명시적으로 "재오픈"을 요청할 때만 done→approved로 처리한다)
4. steps를 편집했다면 마지막 항목이 여전히 "검증:"으로 시작하는지. 아니면 해당 편집만 거부하고 사유를 보고한다.

### B-2. 반영과 관찰 추출

1. 통과한 변경만 tickets.json에 적용한다. 변경된 티켓의 `updated_at`과 파일 `updated_at`을 갱신하고 저장한다.
2. 거부된 항목은 "무엇을 · 왜" 형식으로 보고한다.
3. **관찰 추출**: 변경 전후 diff에서 관찰을 profile.md의 "관찰 로그"에 1줄씩 기록한다 — suggested 반려/승인, steps 수 편집(n→m개), 우선순위 변경, 문구 수정 등. 형식: `YYYY-MM-DD T-xxx(origin·계열) 반려` 처럼 사실만. **해석·패턴화는 붙이지 않는다** (승격은 day-close의 몫).
4. 보드 재생성 → 반영 결과 표(반영/거부·사유)를 보고한다.

## 프로필 기록 규칙 (두 모드 공통)

- 대화 중 일반화 표지("앞으로 · 항상 · 매번 · 하지 마")가 있는 사용자 지시는 임계 없이 **즉시** profile.md의 규칙(R-xx 또는 소통이면 C-xx)으로 기록한다. 근거는 발화 인용과 날짜. 일반화 표지가 없는 일회성 지시("이번엔 빼줘")는 관찰 1건으로만 기록한다.
- 활성 규칙과 모순되는 사용자 행동(예: R-01이 제외하는 계열의 티켓을 직접 요청)도 관찰 로그에 기록한다. 재검토 제안은 day-close가 한다.
- profile.md가 100줄을 넘으면 승격이 끝난 관찰부터 정리한다.

## 보드 재생성 절차 (두 모드 공통)

1. 템플릿을 확보한다. 우선순위:
   - (a) 플러그인의 `skills/ticket-create/assets/board.html` — 읽을 수 있으면 항상 이것을 쓴다 (전체 재생성. 사람이 board.html에 직접 가한 수정은 이때 사라진다)
   - (b) (a)의 읽기가 권한 문제로 차단되면: 기존 `.ticket-pilot/board.html`을 캐리어로 쓴다 — 파일은 그대로 두고 tickets-data 스크립트 내용만 교체
   - (c) 둘 다 불가능하면: "보드 템플릿을 읽을 수 없어 보드 재생성을 건너뛴다"고 보고하고 tickets.json 저장까지만 한다
   - **어떤 경우에도 보드 HTML을 임의로 새로 작성하지 않는다.** 템플릿과 다른 보드는 저장·검증 동작을 보장할 수 없다.
2. 확보한 HTML 안의 `<script id="tickets-data" type="application/json">…</script>` 내용을 현재 tickets.json 전문으로 교체한다. 이때 JSON 문자열 안의 `</`를 `<\/`로 이스케이프한다 (script 태그 조기 종료 방지).
3. 결과를 `.ticket-pilot/board.html`로 저장한다.
