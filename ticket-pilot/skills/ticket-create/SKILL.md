# ticket-create — 티켓 생성 · 보드 변경 반영 · 보드 재생성

## 목적

두 가지 일을 한다. 요청 내용을 보고 모드를 판별한다:
- **A. 티켓 생성**: 사용자 요청을 티켓 초안(draft)으로 만들고, 프로젝트 신호에 근거한 연계 제안(suggested)을 최대 3건 붙인다.
- **B. 보드 변경 반영**: 사용자가 board.html에서 복사해 붙여넣은 JSON(또는 채팅으로 말한 승인·반려·수정)을 검증해 tickets.json에 반영한다. **채팅으로 승인한 티켓은 반영에서 멈추지 않고 실행까지 이어간다 (B-3).**

두 모드 모두 마지막에 board.html을 재생성한다.

## 입력

- `.ticket-pilot/tickets.json` — 티켓 데이터의 **유일한 원본**. 없으면 "먼저 /tp:init 을 실행하세요"라고 안내하고 중단한다.
- CLAUDE.md의 ticket-pilot 블록 (목적 · 성공 기준 SC-x)
- `.ticket-pilot/profile.md` (업무 프로필) · `.ticket-pilot/memory/RECENT_MEMORY.md` · `MIDDLE_MEMORY.md`
- 이 세션에서 사용 가능한 스킬 목록 (기존 스킬 인벤토리)

## 데이터 계약 — tickets.json

```json
{
  "schema_version": 4,
  "project": { "name": "", "goal": "" },
  "updated_at": "2026-07-23T18:00:00+09:00",
  "tickets": [
    {
      "id": "T-001",
      "title": "로그인 폼 유효성 검사 추가",
      "purpose": "사유: (계기) 한 줄\n목적: (완료 시 달성 상태) 한 줄\n효과: (그래서 무엇이 가능해지는지) 한 줄",
      "steps": ["구체 실행 단계 1", "구체 실행 단계 2", "검증: 완료 판정 방법 (필수, 항상 마지막)"],
      "status": "draft",
      "priority": 1,
      "depends_on": [],
      "origin": "user",
      "comments": [
        { "at": "2026-07-24T09:30:00+09:00", "text": "이거 할 때 docs/style-guide.md의 버튼 규칙 참고해서 진행해줘" }
      ],
      "scope": ["src/login.js"],
      "latitude": "strict",
      "rework_of": null,
      "created_at": "…",
      "updated_at": "…",
      "result": null
    }
  ]
}
```

- `status`: `draft | approved | in_progress | blocked | done | rejected`
- `origin`: `user`(사용자 요청 기반) | `suggested`(플러그인 제안)
- `id`: `T-001`부터 순차 부여. 반려·완료 티켓 번호도 재사용하지 않는다 (기존 최대 번호 + 1)
- `priority`: 정수, 낮을수록 먼저 실행
- `comments`: **사용자 전용** 요청·코멘트 배열. 각 항목은 `{ "at": 시각, "text": 내용 }`. 사용자가 보드 모달 또는 채팅("T-003에 코멘트: …")으로 남기며, 실행(ticket-run) 시 지시로 반영된다. **에이전트는 사용자의 명시 지시 없이 comments를 추가·수정·삭제하지 않는다.** 신규 티켓은 `"comments": []`로 만든다
- `scope`: 이 티켓이 **수정할** 파일·디렉터리 경로 배열. steps에서 도출해 채운다. 병렬 실행(ticket-run)의 독립 판정에 쓰인다 — **빈 배열이면 병렬 대상에서 제외되고 직렬로만 실행된다** (보수적 기본). 읽기만 하는 파일은 넣지 않는다
- `latitude`: 실행 재량. `"strict"`(기본 — steps 외 작업 금지, 발견 사항은 보고만) | `"flex"`(scope 안에서 목적에 부합하는 부수 개선 허용, 내역은 결과에 구분 기록). **설정 경로는 사용자 명시 지시("이 티켓은 알아서 개선해도 돼")와 보드 편집뿐이다** — 에이전트가 임의로 flex를 부여하지 않는다. 프로필 기반 자동 설정은 하지 않는다 (보류된 설계)
- `rework_of`: 이 티켓이 **완료(done) 티켓의 산출물을 고치는 수정 티켓**이면 그 원 티켓 ID, 아니면 null. 수정의 수정이면 직전 수정 티켓을 가리킨다(체인). 자기 자신·존재하지 않는 ID 금지. A-3-4 규칙으로만 설정한다
- `result`: 실행 완료 시에만 채워진다 (이 스킬은 null로 만든다)
- **위 필드 외 추가 금지** (태그·담당자·예상시간 등 넣지 않는다)
- 모든 상태 변경은 tickets.json 저장을 동반한다. 저장 시 파일의 `updated_at`을 현재 시각으로 갱신한다.
- **구버전 마이그레이션**: `schema_version`이 1~3인 파일을 읽으면, 각 티켓에 누락 필드를 보충하고(`"comments": []`, `"scope": []`, `"latitude": "strict"`, `"rework_of": null`) `schema_version`을 4로 올린다. 다른 필드는 건드리지 않는다 — 무손실 승격이며, 다음 저장 시 함께 기록하면 된다.

## 공통 선행 — 보드 직접 저장 감지

크로미움 보드는 [tickets.json 연결] 후 [저장]으로 tickets.json을 **직접** 덮어쓴다 (보드가 상태 전환·편집 규칙을 클라이언트에서 이미 검증한다). 따라서 이 스킬은 어느 모드로 들어오든 먼저 확인한다:

1. `.ticket-pilot/board.html`의 `tickets-data` 스냅샷(에이전트가 마지막으로 재생성한 상태)과 tickets.json을 비교한다.
2. 다르면 사용자가 보드에서 직접 저장한 것이다 — tickets.json이 원본이므로 **반영 절차는 필요 없다.** diff에서 B-2의 3(관찰 추출)만 수행하고, 이번 작업 마지막의 보드 재생성으로 스냅샷을 동기화한다.
3. 단, 실행 상태(`in_progress`·`done`·`blocked`) 티켓이 스냅샷과 달라져 있으면 — 보드는 이 변경을 막으므로 손편집 가능성이 있다 — 보고에 경고 1줄을 붙인다.

## A. 티켓 생성 모드

### A-1. 컨텍스트 로드

tickets.json, CLAUDE.md 블록(목적·SC-x), profile.md, RECENT·MIDDLE 메모리를 읽는다.

### A-2. 프로필 시드 (프로필이 비어 있을 때 최초 1회)

profile.md의 규칙·패턴·관찰이 모두 "(아직 없음)"이면:
1. 프로젝트에 의사결정·스타일 지식파일(DECISION_INDEX, 스타일 가이드 등)이 있으면 그것을 프로필 시드로 참조할지 먼저 제안한다.
2. 없으면 3문항 이내로 묻는다: ① 티켓 크기 선호(잘게/크게) ② 제안 적극성(적극/보통/최소) ③ 설명 수준(용어 풀이 필요 여부).
3. 답변은 임계 없이 즉시 profile.md의 규칙으로 기록한다. 근거는 `시드 인터뷰 · 날짜`. 답이 이미 대화에 있으면 묻지 않고 그대로 기록한다.

### A-3. 사용자 요청 티켓 작성

- 티켓 1건 = **1세션 안에 완료 가능한 크기**. 넘치면 분할하고 `depends_on`으로 연결한다.
- `steps`는 하위 모델이 추가 맥락 없이 수행할 수 있게 구체적으로 쓴다. 마지막 항목은 반드시 `"검증:"`으로 시작하는 완료 판정 방법이다. 코드명·버전·정책 ID 같은 실행 디테일은 steps에 담는다 — purpose에 반복하지 않는다.
- 기존 스킬로 처리 가능한 티켓은 steps에 해당 스킬명을 명시한다 (예: "docx 스킬로 보고서 생성").
- **목적 정합 확인**: 요청이 CLAUDE.md의 목적·성공 기준과 연결되지 않으면 생성 전에 1회만 확인한다 — "목적을 갱신할까요, 목적 외 작업으로 표시하고 진행할까요?" 거부가 아니라 확인이다.
- **프로필 적용**: profile.md의 작업 규칙(R-xx)을 티켓 크기·steps 상세도·제안 선별에 적용하고, 적용한 규칙 ID를 문구에 인용한다 (예: "R-02에 따라 steps를 5개 이하로 나눴습니다").
- 모든 신규 티켓은 `draft`로 만들고 `comments`는 빈 배열로 둔다. **자동 승인 금지.** 단, 사용자가 생성 요청에 실행 시 참고 지시를 함께 줬으면("만들고 나서 할 때 ○○ 참고해"), 그 지시를 comments에 `{at, text}`로 기록해도 된다 — 사용자 발화 그대로만.
  - **예외 — 생성과 동시에 승인·실행을 명시 지시한 경우**("만들고 바로 진행해줘", "티켓 만들어서 승인하고 실행까지"): 사용자 승인이지 자동 승인이 아니므로 `approved`로 만들고 B-3의 절차를 그대로 탄다. **"처리해줘"·"해줘" 같은 일반 요청은 여기에 해당하지 않는다** — 승인 또는 즉시 실행을 가리키는 말이 실제로 있을 때만이다. 이 경로에서도 보고에는 만든 티켓의 내용(목적·steps)을 먼저 보여 사용자가 무엇이 실행됐는지 알 수 있게 한다.
- **scope 작성**: steps가 수정·생성할 파일과 디렉터리를 `scope`에 나열한다. 확정할 수 없으면 빈 배열로 두되, 그 티켓은 병렬 실행 대상에서 빠진다는 뜻이다. `latitude`는 기본 `"strict"` — 사용자가 재량 허용을 명시했을 때만 `"flex"`로 기록하고, 그 발화를 comments에도 남긴다.

#### A-3-1. purpose 작성 규칙 — 저맥락 독자 기준

purpose는 정확히 아래 3줄로 쓴다:

```
사유: <이 작업이 필요해진 계기 — 무슨 일이 있었는지>
목적: <끝나면 무엇이 달성돼 있는지 — 완료 상태>
효과: <그래서 무엇이 가능해지거나 달라지는지>
```

원칙:
1. 한 줄에 하나만 담는다 — 나열이 필요하면 steps의 몫이다.
2. 내부 코드·버전·정책 ID(`GLOSSARY_v9.1`, `POL-DLV-070`, `R02` 등)를 넣지 않는다 — steps와 중복이자 소음이다.
3. 약어를 꼭 써야 하면 처음 등장할 때 괄호로 1회만 풀어쓴다.
4. 자체 점검: "이 3줄만 읽고, 이 프로젝트를 모르는 사람이 왜/무엇을/그래서 뭐가 좋아지는지 알 수 있는가?"
5. suggested 티켓의 출처 태그(`[S3·T-003 후속]` 등)는 별도 줄로 맨 앞에 두고, 그다음 줄부터 사유/목적/효과를 쓴다.
6. 기존(구형) 티켓은 강제로 재작성하지 않는다 — board.html이 형식 미준수 시 원문 그대로 표시한다.

나쁜 예 (한 문단에 코드·정책 ID가 뒤섞여, 프로젝트를 모르면 읽을 수 없다):
> "0722 결정 중 추가 결정이 불필요한 기계적 항목만 반영한다: AIV 식별자·GLOSSARY 최종채번(R02), 회사배송부담 폐기 정책 표기·INDEX 정리(R04), 배송건 식별=접수번호 확정(R01, 표기 세부는 개발 정의 범위 명시). R03은 T-007로 분리."

좋은 예 (같은 티켓, 재작성):

```
사유: 0722 회의에서 배송 정책 일부는 결정이 미뤄지고, 바로 반영해도 되는 항목만 남았다.
목적: 추가 논의가 필요 없는 항목(식별자 채번·폐기 정책 표기·배송건 식별 방식)만 먼저 문서에 반영한다.
효과: 확정된 부분부터 반영돼, 남은 결정(R03)이 끝나는 대로 이어서 처리할 수 있다.
```

#### A-3-2. 다단계 요청의 프로세스 분해 — 선행 산출물 규칙

**구현·제작 티켓은 그것이 참조할 선행 산출물(분석·정의·스펙)이 확보된 뒤에만 실행 순서에 온다.** 요청이 "문서(기획서·요구사항서·회의록)를 파악해 무언가를 만드는" 다단계 성격이면, 구현 티켓부터 만들지 않는다.

1. **판정**: 만들려는 티켓이 화면·기능·문서를 "구현/제작"하는 티켓인데, 그 작업이 참조할 정의 산출물(IA 문서, 화면별 스펙, 설계서 등)이 프로젝트에 **파일로 존재하지 않으면** → 정의 단계를 별도 티켓으로 먼저 만들고, 구현 티켓의 `depends_on`에 넣는다.
2. **표준 단계** — 웹 페이지·화면 개발이면 이 순서를 기본으로 한다:
   - ① IA 정리(정보 구조 — 페이지 목록·계층·이동 흐름을 문서로) → ② 화면별 스펙 정의(화면 단위 구성 요소·데이터·동작) → ③ 화면 구현(스펙이 정의된 화면 단위로, 해당 스펙 티켓을 `depends_on`) → ④ 통합 검증.
   - 다른 도메인도 같은 원리다: 분석·정리 → 정의·설계 → 산출·구현 → 검증. **화면 구현(또는 그에 상당하는 산출) 티켓이 실행 선두에 오면 안 된다.**
3. **산출물 연결**: 정의 티켓의 steps에는 산출물을 파일로 남기는 단계와 경로를 명시한다 (예: "docs/IA.md로 저장"). 후행 티켓의 steps에는 그 경로를 입력으로 명시한다 (예: "docs/IA.md의 화면 목록을 입력으로…").
4. **우선순위**: priority는 프로세스 순서대로 오름차순 부여한다. 같은 단계 안의 티켓만 인접 우선순위로 병렬 배치할 수 있다.
5. **예외** — 다음 중 하나면 정의 단계를 생략할 수 있고, 생략 근거를 보고에 1줄 남긴다:
   - 사용자가 "스펙 이미 있음 · 바로 구현"을 명시했거나, 참조할 스펙 문서가 프로젝트에 이미 있다
   - 파일 1~2개 수정 수준의 소규모 단일 작업이다

#### A-3-3. 독립업무 묶음과 수렴 티켓 — 병렬 분해 규칙

같은 단계 안에서 서로의 결과물을 기다릴 필요가 없는 작업들은 **독립업무 묶음**으로 만들어, ticket-run이 서브에이전트로 병렬 실행할 수 있게 한다.

1. **독립 조건 (모두 충족해야 묶음이 된다)**: ① 묶음 안 티켓끼리 depends_on이 없다 (직접·간접 모두) ② scope가 서로 겹치지 않는다 (같은 경로는 물론, 상위·하위 디렉터리 관계도 겹침) ③ 각자 scope가 선언되어 있다. 하나라도 어긋나면 독립이 아니다 — depends_on으로 직렬화하거나, scope가 나뉘도록 티켓을 재분할한다.
2. **배치**: 묶음은 인접 priority로 나란히 배치한다. 단계 간 순서는 A-3-2를 그대로 따른다 (예: 스펙 정의 묶음이 전부 끝나야 구현 묶음이 시작된다).
3. **수렴 티켓 — "추후 업무" 연결**: 묶음의 결과가 최종적으로 하나의 작업(통합, 조립, 통합 검증)으로 이어지면, 그 수렴 티켓을 **묶음과 같은 생성 시점에** draft로 함께 만들고 `depends_on`에 묶음 전체를 넣는다. 실행 자격(의존 전부 done)은 ticket-run이 판정하므로 별도 장치는 필요 없다 — fan-out(병렬) → fan-in(수렴)이 기존 상태 머신 안에서 돈다.
4. **보고**: 병렬 구조를 흐름으로 명시한다 (예: "T-010 ∥ T-011 병렬 가능 → T-012(통합 검토)로 수렴").

#### A-3-4. 수정 티켓 — 완료 산출물에 대한 오류·변경 요청 (상시 티켓화)

done 티켓이 만든 산출물에 대한 오류 신고·변경 요청("저번에 만든 ○○이 안 돼", "그 화면 구성 바꿔줘")은 **그 자리에서 고치지 않고 수정 티켓 초안으로 만든다.** 원 티켓의 result·증빙은 역사 기록이므로 불변이다.

1. **판정**: 요청이 가리키는 산출물을 만든 done 티켓을 찾는다 (result의 files_changed·summary로 확인). 특정되면 수정 티켓으로 만들고, 원 티켓이 없으면(티켓 밖에서 만든 산출물) 일반 티켓으로 만든다.
2. **자동 구성** — 수정 티켓은 다음을 기본으로 채운다:
   - `rework_of`: 원 티켓 ID
   - `scope`: 원 티켓 result.files_changed에서 시작해 요청 범위에 맞게 가감
   - 첫 step: "원 티켓 T-xxx의 result·증빙을 확인한다"
   - 마지막 검증: 이번 수정 확인 + **회귀 확인** — "원 티켓 T-xxx의 기존 검증 절차도 여전히 통과하는지 확인한다"
   - purpose 사유: 무엇이 왜 문제인지 (사용자 표현 기준)
3. **재오픈과의 구분**: 재오픈(done→approved)은 **완료 기록 자체가 틀렸을 때**(검증이 실제로는 실패였음)만, 사용자의 명시 요청으로만 쓴다. 산출물을 바꾸는 요청은 전부 수정 티켓이다.
4. **반복 신호**: 같은 원 티켓을 가리키는 수정 티켓이 이번 건 포함 3건 이상이면 보고에 1줄 알린다 — "T-xxx 관련 수정 3번째입니다. 원 스펙·설계 재검토를 권합니다." **자동 조치는 없다** (알림만).
5. **수정의 수정**: 수정 티켓의 산출물에 다시 수정 요청이 오면 rework_of는 직전 수정 티켓을 가리킨다 — 체인으로 이력이 이어진다.

### A-4. 연계 제안 파이프라인 (suggested 티켓)

원칙: 모든 suggested는 **프로젝트 내부의 구체 신호**에서만 나온다. 출처를 인용하지 못하거나 "왜 지금인가"에 답하지 못하는 후보는 제안하지 않는다. 일반론(테스트 추가·리팩토링·문서화 등)은 그 자체로는 출처가 아니다.

**1단계 — 후보 수집.** 출처는 아래 5개뿐이다 (근거 강도 티어순):

| 티어 | 출처 | 정의 |
|------|------|------|
| T1 | S1 메모리 미해결 | RECENT·MIDDLE의 "미해결/이슈"·"내일 후보" 중 티켓화되지 않은 항목 |
| T1 | S2 블록 해제 | blocked 티켓의 재개 조건을 만드는 선행 작업 |
| T2 | S3 후속 연쇄 | done 티켓의 result.followups |
| T3 | S4 성공 기준 갭 | CLAUDE.md 성공 기준(SC-x) 중 대응 티켓(draft/approved/in_progress/done)이 없는 항목 |
| T4 | S5 스캔 갭 | 파일 스캔에서 발견된 구체 결함 — 목적과의 연결을 명시할 수 있을 때만 |

기존 스킬 인벤토리는 출처가 아니라 **가점 요소**다: 동티어 후보 중 기존 스킬로 즉시 처리 가능한 것을 우선하고, steps에 스킬명을 명시한다.

**2단계 — 필터.** 하나라도 걸리면 탈락:
- F1 프로필 규칙: 활성 R-xx가 제외하는 계열
- F2 반려 이력: rejected 티켓과 실질적으로 같은 제안 (부활은 사용자 명시 요청 시에만)
- F3 중복: 기존 draft·approved·in_progress 티켓과 중복
- F4 크기: 1세션 초과 — 첫 단계만 잘라 제안하거나 제외
- F5 근거 결격: 출처 인용 또는 "왜 지금" 1줄을 채울 수 없는 후보

**3단계 — 랭킹.**
- 1순위: 티어 (T1 > T2 > T3 > T4)
- 동티어: 기존 스킬 가점 → 프로필 패턴(승인율 높은 계열) → 최신 신호
- 상한 3건, 동일 출처 최대 2건
- **신뢰 예산**: origin=suggested이고 결정이 끝난(승인 계열 approved·in_progress·done / 반려 rejected) 최근 10건의 승인율이 1/3 미만이면 상한을 3→1로 낮춘다. 회복 여부 보고는 day-close가 한다.

**4단계 — 근거 명시.**
- 대화 제안 시 각 후보에 3요소: ① 출처 태그와 인용(날짜·티켓 ID·파일) ② "왜 지금" 1줄 ③ 적용한 프로필 규칙 ID (없으면 생략)
- purpose는 출처 태그를 첫 줄에 쓰고, 그다음 줄부터 A-3-1의 사유/목적/효과 형식을 따른다:

  ```
  [S3·T-003 후속]
  사유: T-003 완료 후 로그인 실패 시 에러 안내가 없다는 후속 이슈가 남았다.
  목적: 로그인 실패 케이스에 사용자 안내 메시지를 추가한다.
  효과: 실패 원인을 몰라 반복 시도하던 문의가 줄어든다.
  ```
- suggested도 전부 `draft`로 기록한다.

### A-5. 저장 · 보드 재생성 · 보고

1. tickets.json에 신규 티켓을 추가하고 저장한다 (updated_at 갱신).
2. 아래 "보드 재생성 절차"를 수행한다.
3. 보고: 생성 티켓 표(ID·제목·origin·priority) + suggested 각각의 3요소 근거 + 다단계 분해를 했다면 단계 흐름 1줄(예: "IA 정리 → 화면별 스펙 → 화면 구현 순서로 연결했습니다") + 안내: "board.html을 브라우저로 열어 승인/반려(카드 클릭 또는 드래그)하고 코멘트를 남기세요. 크롬·엣지는 [tickets.json 연결] 후 [저장]으로 파일에 바로 저장되고, 다른 브라우저는 [프롬프트 복사(코워크)]로 복사해 붙여넣으세요. 채팅으로 'T-001 승인해줘'라고 하면 승인과 동시에 실행까지 진행합니다 — 승인만 하려면 '승인만 해줘'라고 하세요."

## B. 보드 변경 반영 모드

트리거: "보드 변경 반영해줘" + 붙여넣은 JSON, 채팅 직접 지시("T-003 승인해줘", "T-002 반려", "T-004에 코멘트: 스타일가이드 참고해줘"), 또는 "보드에서 저장했어"(직접 저장 알림 — 이 경우 반영할 것은 없고 "공통 선행" 절의 감지·관찰만 수행한다).

### B-1. 검증 — 위반 항목은 사유와 함께 거부하고 반영하지 않는다

1. 붙여넣은 JSON의 `schema_version`이 현재 파일과 일치하는가 (채팅 지시는 해당 없음. 1↔2 차이는 거부하지 않고 데이터 계약의 마이그레이션 규칙으로 승격 후 진행한다)
2. 변경 대상 티켓 id가 tickets.json에 존재하는가
3. **허용되는 변경은 `draft ↔ approved ↔ rejected` 간 상태 전환과 필드 편집(title·purpose·steps·priority·depends_on·comments·scope·latitude·rework_of)뿐이다.** `in_progress`·`done`·`blocked` 카드의 변경은 거부한다 — 실행 상태는 실행 스킬만 쓴다. 예외는 둘, 모두 **채팅의 명시 요청일 때만**이다:
   - done 티켓의 **재오픈**("T-005 재오픈해줘") → done→approved
   - blocked 티켓의 **재승인**("T-007 재승인해줘", "막힌 거 다시 진행해줘") → blocked→approved. ticket-run이 안내하는 재개 경로가 이것이다 — 막힌 사유가 해소됐는지는 사용자가 판단한다
4. steps를 편집했다면 마지막 항목이 여전히 "검증:"으로 시작하는지. 아니면 해당 편집만 거부하고 사유를 보고한다.
5. comments를 변경했다면: 각 항목이 `{at, text}` 형식이고 text가 비어 있지 않은지 확인한다. at이 없으면 현재 시각으로 채운다. 채팅으로 받은 코멘트는 사용자 발화 그대로 text에 넣는다 — 요약·재작성하지 않는다.
6. scope를 편집했다면 문자열(파일·디렉터리 경로) 배열인지, latitude는 `strict | flex` 중 하나인지 확인한다. 아니면 해당 편집만 거부하고 사유를 보고한다.
7. rework_of를 편집했다면 null이거나, tickets.json에 존재하는 티켓 ID이고 자기 자신이 아닌지 확인한다. 아니면 해당 편집만 거부하고 사유를 보고한다.

### B-2. 반영과 관찰 추출

1. 통과한 변경만 tickets.json에 적용한다. 변경된 티켓의 `updated_at`과 파일 `updated_at`을 갱신하고 저장한다.
2. 거부된 항목은 "무엇을 · 왜" 형식으로 보고한다.
3. **관찰 추출**: 변경 전후 diff에서 관찰을 profile.md의 "관찰 로그"에 1줄씩 기록한다 — suggested 반려/승인, steps 수 편집(n→m개), 우선순위 변경, 문구 수정, 코멘트 추가(내용 요지 포함: `T-xxx 코멘트 "스타일가이드 참고"`) 등. 형식: `YYYY-MM-DD T-xxx(origin·계열) 반려` 처럼 사실만. **해석·패턴화는 붙이지 않는다** (승격은 day-close의 몫). 보드 직접 저장이 감지된 경우("공통 선행" 절)에도 같은 방식으로 스냅샷 대비 diff에서 관찰을 추출한다.
4. 보드 재생성 → 반영 결과 표(반영/거부·사유)를 보고한다. **채팅 승인이 포함된 반영이면 여기서 보고하고 끝내지 않는다 — B-3으로 이어간다.**

### B-3. 채팅 승인 = 즉시 실행

**채팅 발화로 티켓이 `approved`가 되면, 그 티켓은 같은 턴에서 곧바로 실행까지 간다.** 상태만 바꾸고 "이제 /tp:run 하세요"라고 안내하며 턴을 끝내지 않는다 — 사용자가 승인과 실행을 두 번 요청해야 하는 흐름을 없애는 것이 이 절의 목적이다. **채팅에서의 승인은 곧 실행 지시다.**

1. **적용 조건** (둘 다 참일 때):
   - 이번 요청이 **채팅 발화**로 티켓 상태를 `approved`로 바꿨다 — "T-001 승인해줘", "T-002·T-003 승인", "초안 전부 승인", "T-005 재오픈해줘"(done→approved), "T-007 재승인해줘"(blocked→approved) 모두 해당한다.
   - 사용자가 실행 보류를 명시하지 않았다.
2. **적용 제외** — 아래는 상태 변경까지만 하고 실행하지 않는다:
   - **실행 보류 명시**: "승인만 해줘", "일단 승인만", "실행은 나중에/내일", "승인해두고 기다려". 이때는 보고 끝에 `실행은 "티켓 실행해줘"라고 하시면 이어서 합니다` 1줄을 붙인다.
   - **보드 경로**: 붙여넣은 보드 JSON 반영, "보드에서 저장했어"(직접 저장 감지 — "공통 선행" 절). 보드는 승인 화면이지 실행 지시가 아니다 — 실행은 `/tp:run`으로 시작한다.
   - 승인이 아닌 변경만 있었을 때 (반려·코멘트 추가·필드 편집).
3. **방향은 한쪽뿐이다**: 승인 발화는 실행을 함의하지만, **실행 요청이 승인을 대신하지는 않는다.** 초안 티켓에 대한 "T-003 실행해줘"는 이 절이 아니라 ticket-run의 실행 거부 규칙(승인 여부 확인)으로 간다.
4. **실행 대상 범위**: **이번 발화로 승인된 티켓만**이다. 이전부터 approved였던 티켓은 사용자가 함께 지목했을 때("승인하고 밀린 것까지 다 실행해줘")만 포함한다 — 보드에서 승인만 해 두고 아직 실행하지 않은 티켓이 갑자기 도는 일을 막는다.
5. **인계 방법**: B-2의 저장과 보드 재생성을 **먼저 끝낸 뒤**, Skill 도구로 `tp:ticket-run` 스킬을 호출해 그 실행 프로토콜을 그대로 태운다 (Skill 도구를 쓸 수 없으면 `${CLAUDE_PLUGIN_ROOT}/skills/ticket-run/SKILL.md`를 읽어 그대로 실행한다). 호출 시 4의 티켓 ID 목록을 대상 범위로 함께 넘긴다. **이 스킬이 직접 실행하지 않는다** — 선점 기록(in_progress 선저장)·의존성 자격 판정·scope 검증·증빙 수집 같은 실행 통제는 전부 ticket-run의 몫이고, 우회 경로를 만들지 않는다.
6. **실행 자격이 없을 때**: 승인된 티켓의 `depends_on`에 done이 아닌 티켓이 있으면 ticket-run이 대기로 판정한다. 승인은 그대로 두고 무엇을 기다리는지 보고한다 (예: "T-012는 T-010·T-011 완료 후 자격을 얻습니다"). 기다리는 선행 티켓이 이미 approved인데 아직 실행되지 않았다면 그 사실도 함께 알린다 — 그 티켓까지 실행할지는 사용자가 정한다. **자격을 만들려고 선행 티켓을 임의로 승인하지 않는다.**
7. **보고**: 승인 반영과 실행 결과를 **한 번의 보고로** 낸다 — ① 반영 표(B-2의 4) ② 실행 결과(ticket-run의 마무리 3가지: 후속 제안 표·blocked 요약·실행 요약). 승인 사실만 보고하고 턴을 끝내는 것은 이 절 위반이다.

## 프로필 기록 규칙 (두 모드 공통)

- 대화 중 일반화 표지("앞으로 · 항상 · 매번 · 하지 마")가 있는 사용자 지시는 임계 없이 **즉시** profile.md의 규칙(R-xx 또는 소통이면 C-xx)으로 기록한다. 근거는 발화 인용과 날짜. 일반화 표지가 없는 일회성 지시("이번엔 빼줘")는 관찰 1건으로만 기록한다.
- 활성 규칙과 모순되는 사용자 행동(예: R-01이 제외하는 계열의 티켓을 직접 요청)도 관찰 로그에 기록한다. 재검토 제안은 day-close가 한다.
- profile.md가 100줄을 넘으면 승격이 끝난 관찰부터 정리한다.

## 보드 재생성 절차 (두 모드 공통)

1. 템플릿을 확보한다. 우선순위:
   - (a) 플러그인의 `skills/ticket-create/assets/board.html` — 읽을 수 있으면 항상 이것을 쓴다 (전체 재생성. 사람이 board.html에 직접 가한 수정은 이때 사라진다)
   - (b) (a)의 읽기가 권한 문제로 차단되면: 기존 `.ticket-pilot/board.html`을 캐리어로 쓴다 — 파일은 그대로 두고 tickets-data 스크립트 내용만 교체
   - (c) 둘 다 불가능하면: "보드 템플릿을 읽을 수 없어 보드 재생성을 건너뛴다"고 보고하고 tickets.json 저장까지만 한다
   - **어떤 경우에도 보드 HTML을 임의로 새로 작성하지 않는다.** 템플릿과 다른 보드는 저장·검증 동작을 보장할 수 없다.
2. 확보한 HTML 안의 `<script id="tickets-data" type="application/json">…</script>` 내용을 현재 tickets.json 전문으로 교체한다. 이때 JSON 문자열 안의 `</`를 `<\/`로 이스케이프한다 (script 태그 조기 종료 방지).
3. 결과를 `.ticket-pilot/board.html`로 저장한다.
