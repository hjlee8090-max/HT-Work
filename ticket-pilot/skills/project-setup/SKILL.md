# project-setup — 프로젝트 초기 세팅

## 목적

현재 프로젝트에 Ticket Pilot 작업 환경을 만든다. 산출물은 2가지다:
1. `CLAUDE.md`의 ticket-pilot 관리 블록 — 모든 세션이 읽는 프로젝트 컨텍스트
2. `.ticket-pilot/` 워크스페이스 — 티켓·메모리·프로필 데이터 파일

## 입력

- 현재 프로젝트 루트 (작업 디렉터리)
- 사용자가 함께 준 추가 설명이 있으면 인터뷰 답변으로 사용한다

## 실행 단계

### 1. 프로젝트 스캔

1. 루트에서 2단계 깊이까지 디렉터리 구조를 파악한다. `.gitignore`가 무시하는 경로는 스캔하지 않는다.
2. 핵심 파일을 읽는다: README, package.json 또는 이에 준하는 매니페스트(pyproject.toml, go.mod 등), 진입점 파일.
3. 파일이 300개를 넘으면 전수 스캔을 중단하고 요약 스캔으로 전환한다: 최상위 디렉터리 목록 + 핵심 파일만.
4. 스캔 결과로 "이 프로젝트는 무엇인가"를 1~2문장으로 추정해 둔다 (3단계 인터뷰에서 사용).

### 2. 기존 스킬 인벤토리

1. 다음 3곳에서 스킬의 name + description을 수집한다:
   - `<프로젝트 루트>/.claude/skills/*/SKILL.md`
   - `~/.claude/skills/*/SKILL.md`
   - 이 세션에 로드된 다른 플러그인·스킬 목록 (시스템에 표시된 사용 가능 스킬. `claude plugin list` CLI가 있으면 보조로 사용)
2. 수집 결과를 표(이름 · 한 줄 설명)로 **대화에 보고**한다. 티켓 생성 시 "기존 스킬로 처리 가능한 작업"을 찾는 데 쓰이므로 누락 없이 수집한다.
3. **트리거 충돌 감지**: Ticket Pilot의 트리거 문구 — "하루 마감", "오늘 마감", "티켓", "메모리 정리", "프로젝트 세팅", "중간 정리", "핸드오프", "세션 넘겨줘" — 와 겹치는 트리거를 가진 기존 스킬이 있으면 충돌 목록(스킬명 · 겹치는 문구)을 사용자에게 보고하고, 겹치는 상황에서는 명시적 커맨드(/tp:*)를 쓰라고 안내한다.

### 3. 목적 인터뷰

1. 질문은 최대 3개: **목적 · 사용자(이해관계자) · 성공 기준**.
2. 스캔으로 추정 가능한 항목은 추정치를 먼저 제시하고 확인만 받는다. 답이 이미 대화에 있으면 다시 묻지 않는다.
3. 성공 기준은 번호 목록(SC-1, SC-2, …)으로 정리한다. 이 번호는 이후 연계 제안이 "성공 기준에 대응하는 티켓이 있는가"를 판정하는 기준이 된다.

### 4. CLAUDE.md 관리 블록 작성

아래 템플릿의 `{…}`를 인터뷰 결과로 채워 CLAUDE.md에 쓴다.

```markdown
<!-- ticket-pilot:begin — 이 블록은 ticket-pilot이 관리합니다. init 재실행 시 갱신됩니다 -->
# 프로젝트 컨텍스트 (ticket-pilot)

## 배경과 목적
- 목적: {인터뷰 결과}
- 사용자/이해관계자: {인터뷰 결과}
- 성공 기준: SC-1 {…} / SC-2 {…} — 반드시 번호 목록으로 쓴다

## 작업 규칙
1. 실행 작업은 .ticket-pilot/tickets.json의 approved 티켓에 근거한다.
   티켓 없는 실행 요청 — 완료된 작업 산출물의 수정 요청 포함 — 을 받으면 먼저 티켓 초안을 제안한다.
   사용자가 채팅으로 승인한 티켓("T-001 승인해줘")은 상태만 바꾸고 끝내지 않고 그 자리에서 실행까지 진행한다
   (ticket-run 프로토콜 그대로. "승인만 해줘"라고 하면 상태만 바꾼다).
2. 지시·계획 문서는 하위 모델이 추가 맥락 없이 수행할 수 있게 쓴다.
   순서: 목적 → 입력 → 실행 단계 → 완료 기준(검증 방법).
3. 세션 시작 시 .ticket-pilot/HANDOFF.md가 "대기" 상태면 먼저 확인하고(중단된 세션의 인계장),
   .ticket-pilot/memory/RECENT_MEMORY.md의 최근 3일 엔트리를 확인한다.
4. CLAUDE.md 전체는 200줄을 넘기지 않는다. 넘칠 내용은 별도 문서로 분리해 링크한다.

## 소통 방식 (기본값 + 학습 규칙 · day-close가 동기화)
적용 범위: 사용자에게 보이는 글 — 보고, 제안, 논의, 티켓의 title·purpose. 하위 모델용 지시문(steps)과 코드는 정밀성을 우선한다.
1. 약어·전문 용어는 처음 쓸 때 한 줄로 풀어 쓴다. 파일·함수명은 역할과 함께 말한다.
2. 보고와 제안은 결론 → 근거 → 세부 순서로 쓴다.
3. 용어 설명·재설명·"쉽게/짧게" 요청을 받으면 .ticket-pilot/profile.md 관찰 로그에 1줄 기록한다.

## 명령
/tp:init · /tp:tickets · /tp:run · /tp:done · /tp:handoff(세션 인계)
<!-- ticket-pilot:end -->
```

쓰기 규칙 (엄수):
- CLAUDE.md에 begin/end 마커가 이미 있으면 **마커 사이만** 교체한다. 마커가 없으면 파일 끝에 블록을 추가한다. CLAUDE.md 자체가 없으면 새로 만든다.
- 마커 밖의 사용자 작성 내용은 절대 수정·삭제하지 않는다.
- 블록은 60줄 이하를 유지한다. '소통 방식' 절은 12줄 이하를 유지한다.
- 파일 전체가 200줄을 넘으면 경고만 하고 침범하지 않는다.
- init은 블록 전체를 갱신할 수 있지만, 재실행 시 이미 승격된 소통 규칙(C-xx 줄)이 블록에 있으면 보존한다.

### 5. .ticket-pilot/ 워크스페이스 생성

이미 존재하는 파일은 **건드리지 않고** 누락된 것만 만든다 (재실행 안전). 데이터 초기화는 사용자가 명시적으로 요청할 때만 한다.

| 경로 | 초기 내용 |
|------|-----------|
| `.ticket-pilot/config.json` | 아래 config 템플릿 |
| `.ticket-pilot/tickets.json` | 아래 tickets 템플릿 (인터뷰 결과로 project 채움) |
| `.ticket-pilot/memory/RECENT_MEMORY.md` | `# RECENT_MEMORY — 최근 7일 (일 단위 엔트리)` 한 줄 |
| `.ticket-pilot/memory/MIDDLE_MEMORY.md` | `# MIDDLE_MEMORY — 7~30일 (주 단위 요약)` 한 줄 |
| `.ticket-pilot/memory/LONG_MEMORY.md` | `# LONG_MEMORY — 30일 초과 (월 단위 핵심)` 한 줄 |
| `.ticket-pilot/profile.md` | 아래 profile 템플릿 |
| `.ticket-pilot/artifacts/.gitkeep` | 빈 파일 (증빙 저장 폴더 유지용) |
| `.ticket-pilot/board.html` | 플러그인의 `skills/ticket-create/assets/board.html`을 복사한 뒤, 그 안의 `<script id="tickets-data" …>` 내용을 방금 만든 tickets.json 전문으로 교체 (JSON 안의 `</`는 `<\/`로 이스케이프). **보드 HTML을 임의로 작성하지 않는다** — 이후 티켓 스킬들이 이 파일을 캐리어 삼아 데이터만 교체한다 |

config.json — 키 2개만. 키 추가 금지:

```json
{ "screenshot": "auto", "memory": { "recent_days": 7, "middle_days": 30 } }
```

tickets.json — 티켓 데이터의 유일한 원본. 빈 초기 상태:

```json
{
  "schema_version": 4,
  "project": { "name": "{프로젝트명}", "goal": "{목적 1줄}" },
  "updated_at": "{현재 시각 ISO 8601, 예: 2026-07-23T10:00:00+09:00}",
  "tickets": []
}
```

profile.md — 업무 프로필 초기 템플릿:

```markdown
# 업무 프로필 (ticket-pilot 관리 · 마지막 갱신: {오늘 날짜})

## 규칙 — 작업 (티켓 생성 시 적용)
(아직 없음)

## 규칙 — 소통 (day-close가 CLAUDE.md에 동기화)
(아직 없음)

## 패턴 (승격 대기 후보)
(아직 없음)

## 관찰 로그 (원시 신호 · 승격되면 근거 요약만 남기고 삭제)
(아직 없음)
```

커밋 정책: `.ticket-pilot/`은 artifacts까지 **전체 커밋 대상**이다. .gitignore 항목을 만들지 않는다. 단 하나의 예외 — `git remote`가 있는 공유 저장소로 보이면, profile.md(개인 업무 성향 기록)가 원격에 노출된다는 사실을 알리고 커밋에서 제외할지 1회 확인한다. 제외를 선택하면 `.gitignore`에 `.ticket-pilot/profile.md`만 추가한다.

git 커밋 자체는 자동으로 하지 않는다. 생성 파일 목록을 보고하고 커밋을 제안만 한다.

- [ ] 마커 밖 기존 내용이 그대로다 (재실행 시에도)
- [ ] `.ticket-pilot/` 아래 7개 항목이 모두 존재한다
- [ ] 스킬 인벤토리와 충돌 목록이 대화에 보고되었다
- [ ] 보고 마지막에 다음 단계를 안내한다: "/tp:tickets 로 첫 티켓을 만드세요. 크롬·엣지를 쓴다면 .ticket-pilot/board.html을 열어 [tickets.json 연결]을 한 번 해 두세요 — 이후 보드의 승인·코멘트가 [저장] 버튼으로 tickets.json에 바로 저장됩니다. 채팅으로 'T-001 승인해줘'라고 하면 승인과 동시에 실행까지 진행됩니다"
