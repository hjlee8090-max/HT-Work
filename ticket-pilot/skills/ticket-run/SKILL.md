# ticket-run — 승인된 티켓의 실행 (직렬 기본 · 독립업무는 병렬)

## 목적

`.ticket-pilot/tickets.json`의 approved 티켓을 우선순위·의존성 순으로 실행하고, 결과와 증빙을 기록한다. 기본은 1건씩 직렬이되, **서로 독립인 티켓 묶음(상호 의존 없음 + scope 서로소)은 tp-worker 서브에이전트로 병렬 실행**한다. 핵심 통제 3가지:
- **승인된 티켓만 실행한다.** draft·rejected 실행 요청은 거부하고 승인 절차를 안내한다.
- **같은 티켓을 두 번 실행하지 않는다.** 실행 시작 전에 in_progress를 저장해 세션이 끊겨도 중복이 없다.
- **tickets.json은 오케스트레이터(이 스킬을 실행하는 세션)만 쓴다.** 워커는 프로젝트 파일 작업만 하고 보고를 반환한다 — 상태·결과 기록의 주체는 항상 하나다.

## 입력

- `.ticket-pilot/tickets.json` — 유일한 원본. 없으면 "/tp:init 먼저"를 안내하고 중단
  - 사용자가 크로미움 보드에서 [저장]으로 직접 갱신했을 수 있다 — 정상이다. 파일에 있는 상태가 곧 승인 상태다.
  - `schema_version`이 1·2인 파일은 각 티켓에 누락 필드를 보충하고(`comments:[]`, `scope:[]`, `latitude:"strict"`) `schema_version`을 3으로 올려서 다음 저장 시 함께 기록한다 (무손실 승격)
- `.ticket-pilot/config.json` (screenshot 설정)
- 이 세션에서 서브에이전트(Agent/Task) 도구를 쓸 수 있는지 — 없으면 전 티켓 직렬 실행으로 폴백한다
- 사용자가 특정 티켓 ID를 지정했으면 그 티켓(들)만 대상으로 한다 (단, 아래 프로토콜의 자격·독립 검사는 동일하게 적용)

## 실행 프로토콜 (순서 엄수)

1. **로드와 중단 복구 확인**: tickets.json을 읽고 파일의 `updated_at`을 기억한다(로드 시점 값). `in_progress` 티켓이 이미 있으면 — 직전 세션이 중단된 상황이다(병렬 배치였다면 여러 건일 수 있다) — **사용자에게 질의한다**: "T-xxx(…)가 진행중 상태로 남아 있습니다. 이어서 재개할까요, 보류(blocked)로 돌릴까요?" 자동으로 결정하지 않는다. 재개를 선택하면 이미 완료된 단계를 파일 상태로 확인하고 남은 단계부터 이어간다(같은 변경을 두 번 가하지 않는다).

2. **배치 선정**: 자격 있는 티켓 = `status=approved`이고 `depends_on`의 티켓이 **전부 done**. 자격 티켓을 priority 오름차순(동률이면 ID 오름차순)으로 정렬해 첫 번째를 배치에 넣고, 이어지는 자격 티켓 중 아래를 **모두** 만족하는 것을 배치에 추가한다 (배치 상한 3건):
   - 배치 안 모든 티켓과 서로 의존 관계가 없다 (직접·간접 모두 — depends_on 그래프로 확인)
   - `scope`가 비어 있지 않고, 배치 안 모든 티켓의 scope와 겹치지 않는다 (**같은 경로는 물론, 한쪽이 다른 쪽의 상위·하위 디렉터리인 경우도 겹침으로 본다.** scope 미선언(빈 배열) 티켓은 병렬 대상이 아니다 — 단독 직렬로만 실행)
   - 자격 티켓이 없으면 6단계로 간다. depends_on이 done이 아닌 approved만 남았으면 그 사실을 보고한다.
   
   배치가 2건 이상이고 서브에이전트 도구가 있으면 → **4-B (병렬)**. 아니면 배치 첫 티켓만 → **4-A (직렬)**.

3. **선점 기록(중복 방지)**: 배치의 **전 티켓**을 `in_progress`로, 각 티켓과 파일의 `updated_at`을 현재 시각으로 바꿔 **한 번의 저장으로 선점부터 한다.** 저장이 끝난 뒤에만 실행을 시작한다.
   - **동시 세션 가드**: 이 저장 직전(이후 5단계의 모든 저장도 동일) 파일의 `updated_at`을 다시 읽어 로드 시점 값과 비교한다. 달라져 있으면 다른 세션이 이 파일을 고친 것이다 — 실행을 중단하고 "다른 세션의 변경이 감지되어 중단했다"고 보고한다. 실행(run) 세션은 동시에 1개만 전제한다.

4. **실행**

   **4-A. 직렬 (기본)**: 티켓의 `steps`를 순서대로 수행한다. 마지막 "검증:" 단계의 통과를 실제로 확인한다.
   - **코멘트 반영 (steps 수행 전에 확인)**: 티켓의 `comments`는 사용자가 이 티켓에 남긴 보충 지시다 — steps와 함께 실행 지침으로 취급한다.
     - 코멘트가 참고 자료를 지정하면("○○ 참고해서") 해당 파일·문서를 **실행 전에 읽고** 그 내용에 맞춰 수행한다. 처리 방식을 지정하면("○○로 처리해줘") 그 방식으로 수행한다.
     - 반영한 코멘트는 result.summary에 1줄로 명시한다 (예: "코멘트 반영: docs/style-guide.md의 버튼 규칙 적용").
     - 코멘트가 steps·purpose와 모순되거나 티켓을 1세션 크기 밖으로 키우면: **실행하지 말고** status를 `blocked`로 바꿔 저장한 뒤, 어떤 코멘트가 왜 충돌하는지 보고한다 (해소는 사용자 결정 — 티켓 수정 후 재승인).
     - 코멘트를 에이전트가 추가·수정·삭제하지 않는다. 완료 후에도 남겨 둔다 (기록이다).
   - **재량(latitude) 준수**: `strict`(기본)면 steps 외 작업 금지 — 발견 사항은 result.followups에 기록만. `flex`면 scope 안에서 티켓 목적에 부합하는 부수 개선 허용 — 한 일은 result.summary에 "재량:" 접두로 구분 기록.
   - **티켓 범위 밖 작업이 필요해 보이면: 하지 않는다.** 대신 result.followups에 한 줄로 기록만 한다. (예: 실행 중 발견한 버그, 하는 김에 좋아 보이는 개선) 단, 코멘트가 지시한 작업은 범위 안이다.
   - 실행이 실패하거나 외부 조건(누락 파일, 권한, 의존성)에 막히면: status를 `blocked`로 바꿔 저장하고, 사유와 재개 조건을 대화에 보고한 뒤 2단계로 돌아간다. blocked의 재실행은 사용자가 재승인(approved로 복귀)한 뒤에만 한다.

   **4-B. 병렬 (독립업무 배치)**: 티켓당 워커 서브에이전트 1개를 **한 메시지에 동시** 스폰한다.
   - 에이전트 타입: 사용 가능 목록에 `tp-worker`(플러그인 제공)가 있으면 그것을 쓴다. 없으면 범용 서브에이전트를 쓰되, `${CLAUDE_PLUGIN_ROOT}/agents/tp-worker.md`의 "절대 규칙"과 "보고 형식"을 읽어 지시서 맨 앞에 전문으로 포함한다.
   - 워커는 세션 맥락을 모른다 — 지시서는 **자족적**으로 쓴다. 티켓당 지시서 템플릿:

     ```
     [Ticket Pilot 작업 지시서 — T-xxx]
     프로젝트: {project.name} — {project.goal}
     성공 기준: {CLAUDE.md 블록의 SC-x 발췌}
     목적: {purpose 전문}
     단계: {steps 전문 — 마지막 "검증:" 단계를 실제로 수행할 것}
     사용자 코멘트: {comments 전문. 지시로 반영하고, 참조 문서는 작업 전에 읽을 것. 없으면 "(없음)"}
     수정 허용 범위(scope): {scope 목록} + .ticket-pilot/artifacts/T-xxx/ (증빙 전용)
     재량: {latitude가 strict면 "엄격 — 단계에 적힌 것만. 발견 사항은 followups로만 보고" / flex면 "유연 — 단계 완수 후 범위 안 부수 개선 허용, 전부 discretionary에 기록"}
     보고: 마지막 메시지는 보고 형식의 JSON 하나만.
     ```
   - 워커 실행 중 오케스트레이터는 프로젝트 파일을 수정하지 않는다 (충돌 방지).

5. **수렴·검증·완료 기록**: 각 워커의 보고(직렬이면 자체 실행 결과)에 대해 순서대로 처리한다. **저장은 항상 오케스트레이터가 티켓별로 순차 수행한다.**
   1. **scope 검증**: 보고의 `files_changed`가 전부 scope(+ 자기 artifacts 폴더) 안인지 확인한다. 이탈 → done으로 기록하지 않고 `blocked` + "범위 이탈: <파일 목록>"을 보고한다. 커밋 전이므로 git으로 되돌릴 수 있음을 안내한다 (자동 되돌리기는 하지 않는다 — 사용자 결정).
   2. **재량 검증**: `strict` 티켓의 files_changed에 steps와 무관한 변경이 섞여 있으면 1과 동일하게 처리한다. `flex` 티켓은 `discretionary` 내역을 result.summary에 "재량:" 접두로 병기한다.
   3. `ok:false` → `blocked` + blocked_reason 저장·보고.
   4. 통과 → status를 `done`으로 바꾸고 `result`를 채워 저장한다:

   ```json
   {
     "summary": "무엇을 했는지 3문장 이내 (+ 코멘트 반영·재량 내역)",
     "files_changed": ["src/login.js"],
     "evidence": [ { "type": "screenshot", "path": "artifacts/T-001/shot1.png", "note": "" } ],
     "followups": ["실행 중 발견한 후속 작업 요약 (티켓화는 ticket-optimize가 제안)"],
     "completed_at": "2026-07-23T18:00:00+09:00"
   }
   ```

   - `evidence.type`은 `screenshot | diff | file` 중 하나 (수집 규칙은 아래). 워커가 반환한 evidence를 쓰되, 없으면 diff 타입 최소 1건을 오케스트레이터가 만든다.
   - 배치의 전 티켓 기록이 끝나면 board.html을 재생성한다 (재생성 절차는 이 문서 마지막 절).

6. **반복과 마무리**: 자격 있는 approved가 소진될 때까지 2~5를 반복한다. 병렬 배치의 의존 티켓(수렴 티켓)은 배치가 done이 되는 즉시 다음 회차에 자연히 자격을 얻는다. 끝나면 **ticket-optimize 스킬을 자동 호출**하고(완료 티켓 정리·후속 제안·리포트 갱신), 실행 요약을 보고한다 — 배치 구성을 명시한다 (예: "배치 1: T-010 ∥ T-011 병렬 → 배치 2: T-012 · 완료 3건 · blocked 0건").

### 실행 거부 규칙

- `draft`·`rejected` 티켓의 실행 요청 → 거부: "승인되지 않은 티켓입니다. board.html에서 승인하거나 'T-xxx 승인해줘'라고 말한 뒤 실행하세요."
- `done` 티켓의 재실행 요청 → 재오픈 절차 없이는 **절대 거부**: "이미 완료된 티켓입니다. 다시 실행하려면 'T-xxx 재오픈해줘'라고 명시적으로 요청하세요." 재오픈(done→approved)은 사용자의 명시 요청에만 처리하고, 그 후 일반 프로토콜로 실행한다.

## 증빙 수집 규칙

- 다음 3조건이 모두 참이면 결과 화면을 캡처한다: ① config.json의 `screenshot`이 `"auto"` ② 웹 프로젝트다(열 수 있는 HTML/URL이 있다) ③ 캡처 수단이 있다(Playwright 등).
  - 저장 위치: `.ticket-pilot/artifacts/T-XXX/` · **티켓당 최대 2장 · PNG 폭 1280px 이하** (저장소 용량 상한)
  - evidence에 `{ "type": "screenshot", "path": "artifacts/T-XXX/…", "note": "…" }`로 기록 (board.html 기준 상대 경로)
  - 병렬 실행 시 워커는 **자기 티켓의 artifacts 폴더에만** 저장할 수 있다.
- 캡처 수단이 없으면 설치를 제안해도 된다. 단 **설치·캡처의 실패가 티켓 실패로 이어져서는 안 된다** — 실패 시 조용히 대체 경로로 간다.
- 캡처 불가 시 대체: `diff` 또는 `file` 타입으로 기록한다. 증빙 없는 done은 만들지 않는다 (최소 diff 요약 1건).
- evidence 항목은 타입과 무관하게 **path와 note 키를 모두 가진다**:
  - `screenshot`: path=이미지 상대 경로(`artifacts/T-XXX/…`), note=화면 설명 1줄
  - `diff`: path=변경 파일명(여러 개면 쉼표 연결), note=변경 요약 1줄
  - `file`: path=산출물 경로, note=무엇인지 1줄

## 보드 재생성 절차

1. 템플릿 확보 우선순위: (a) 플러그인의 `skills/ticket-create/assets/board.html` → (b) 권한 차단 시 기존 `.ticket-pilot/board.html`을 캐리어로 사용 → (c) 둘 다 불가 시 재생성을 건너뛰고 보고. **보드 HTML을 임의로 새로 작성하지 않는다.**
2. HTML 안의 `<script id="tickets-data" type="application/json">…</script>` 내용을 tickets.json 전문으로 교체한다 (`</` → `<\/` 이스케이프).
3. `.ticket-pilot/board.html`로 저장한다.

## 완료 기준

- [ ] 실행된 모든 티켓이 approved → in_progress(선저장) → done/blocked 경로만 거쳤다
- [ ] 병렬 배치는 전 티켓이 상호 의존 없음 + scope 서로소였고, tickets.json 저장은 오케스트레이터만 수행했다
- [ ] done 티켓 전건에 result(summary·files_changed·evidence·completed_at)가 있고, files_changed가 scope를 벗어나지 않았다
- [ ] comments가 있던 티켓은 반영 내역이 summary에 있거나, 충돌로 blocked 처리되고 사유가 보고되었다
- [ ] strict 티켓에 steps 외 변경이 없다 (flex의 재량 내역은 summary에 구분 기록됨)
- [ ] 미승인·완료 티켓을 실행하지 않았다
- [ ] board.html이 최신 상태다
- [ ] ticket-optimize가 호출되었고 실행 요약(배치 구성 포함)이 보고되었다
