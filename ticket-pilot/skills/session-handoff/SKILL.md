# session-handoff — 세션 인계 (중간 정리 · 재개)

## 목적

세션이 불안정할 때 지금까지의 작업 맥락을 파일로 고정하고, 다음 세션이 손실 없이 이어받게 한다. 두 모드를 가진다:
- **A. 정리 모드**: 인계장 `.ticket-pilot/HANDOFF.md` 저장 → 재개 프롬프트 제공
- **B. 재개 모드**: 인계장을 읽고 정합성 검증 → 재개 브리핑 → 이어서 진행

day-close와의 구분: 이 스킬은 **중간 정리**다 — tickets.json·메모리·프로필·CLAUDE.md를 수정하지 않는다. 기록은 인계장 하나뿐이며, 하루 기록·압축·규칙 승격은 day-close의 몫이다.

## 입력

- `.ticket-pilot/tickets.json` (읽기만 — in_progress·approved 파악). 없으면 "/tp:init 먼저"를 안내하고 중단
- 이번 세션의 대화 (결정·지시·대기 질문·진행 상황)
- git 상태 (커밋 안 된 변경 파악 — git이 없으면 이 항목은 "확인 불가"로 기록)

---

## A. 정리 모드

**원칙: 저장이 보고보다 먼저다.** 세션이 불안정하다는 전제이므로 A-1(파일 저장)을 끝낸 뒤에만 A-2(보고)를 한다. 수집에 오래 걸릴 것 같으면 아는 것만으로 먼저 저장하고 보강한다.

### A-1. HANDOFF.md 저장

현재 상태를 수집해 `.ticket-pilot/HANDOFF.md`에 아래 템플릿으로 **덮어쓴다** (유효한 인계장은 항상 1개 — 과거 인계장은 git 히스토리에 있다). 덮어쓰기 직전 파일을 다시 읽어, **다른 세션이 방금 만든 "대기" 상태 인계장이 있으면 덮어쓰지 않고** 그 사실을 보고해 선택을 받는다 (그 세션의 인계 맥락을 지우게 된다). 저장 후 `.ticket-pilot/journal.ndjson`에 1줄 덧붙인다: `{"at":"<ISO8601>","session":"<세션 4자리 ID>","actor":"session-handoff","op":"write","file":"HANDOFF.md","note":"인계장 저장 — <사유>"}`. 규약 전문은 `${CLAUDE_PLUGIN_ROOT}/references/safe-write.md`.

```markdown
# 세션 핸드오프 (ticket-pilot 관리)
- 생성: 2026-07-24T15:42:00+09:00 · 사유: {사용자가 말한 이유 1줄, 없으면 "중간 정리"} · 상태: 대기

## 지금 하던 일
- T-012 (in_progress) — 단계 3개 중:
  - [x] 1. 두 스펙 문서 대조표 작성
  - [ ] 2. 어긋난 항목 통일안으로 수정  ← 다음 여기부터
  - [ ] 3. 검증: 용어 대조 확인
- 컨텍스트 메모: {이번 세션에서 알아낸 함정·실패한 접근·중요 판단 1~3줄}

## 대화에서 결정됐지만 아직 파일에 반영 안 된 것
- {결정 내용 — 어느 티켓/파일에 반영해야 하는지 포함. 없으면 "없음"}

## 사용자 답변 대기
- {물어봤지만 답을 못 받은 것. 없으면 "없음"}

## 다음 행동 (순서대로)
1. {구체 행동 1~3개. 예: /tp:run → T-012 재개 질의에서 "재개" 선택, 2단계부터}

## 작업 트리 상태
- 커밋 안 된 변경: {파일 목록 또는 "없음"} · 마지막 커밋: {해시 제목}

## 재개 시 읽을 파일
- {경로 목록 — tickets.json의 해당 티켓, 관련 스펙·문서, RECENT_MEMORY 최근 엔트리 등}
```

작성 규칙:
- **하던 일 체크리스트는 파일 상태로 확인해서 쓴다** — 대화 기억이 아니라 실제 산출물 기준. in_progress 티켓이 없으면 "실행 중 티켓 없음"으로 쓰고, 진행 중이던 비티켓 작업(논의·기획)을 적는다.
- **새 정보만 담는다** — tickets.json에 이미 있는 내용(steps 전문 등)을 복사하지 않는다. 체크 상태·메모·결정만.
- **tickets.json은 수정하지 않는다** — in_progress는 그대로 둔다. 재개는 ticket-run의 복구 질의가 담당하고, 인계장의 체크리스트는 그 판단을 뒷받침하는 정보다.

### A-2. 보고 + 재개 프롬프트

1. 인계 요약을 보고한다: 하던 일 · 미반영 결정 · 대기 질문 · 다음 행동.
2. 커밋 안 된 변경이 있으면 커밋을 **1회 제안**한다 (자동 커밋은 하지 않는다. 컨테이너·클라우드 세션처럼 파일이 사라질 수 있는 환경이면 커밋을 강하게 권한다).
3. 재개 프롬프트를 코드블록으로 제공하고 "새 세션의 첫 메시지로 붙여넣으세요"라고 안내한다:

```
[Ticket Pilot 재개] .ticket-pilot/HANDOFF.md(7/24 15:42 생성)를 읽고 이어서 진행해줘.
대조 요약: T-012 실행 중(잔여 2/3단계) · 미반영 결정 1건 · 다음 행동 = T-012 재개.
핸드오프 이후 tickets.json이 바뀌었으면 차이부터 보고해줘.
```

- 프롬프트는 **포인터 + 대조 요약 2줄**만 담는다. 상태 전문은 파일에 있다 (원본은 1곳 원칙). 요약은 파일 유실·불일치 시의 최소한의 방향이자, 재개 모드의 정합성 검증 재료다.

## B. 재개 모드

트리거: "[Ticket Pilot 재개]"로 시작하는 프롬프트, 또는 "이어서 진행해줘"류 요청 + 소비 안 된 HANDOFF.md 존재.

1. `.ticket-pilot/HANDOFF.md`를 읽는다. 없으면: "인계장이 없습니다. RECENT_MEMORY 최근 엔트리로 맥락을 잡을까요?"라고 안내하고 중단한다.
2. **정합성 검증** — 어긋나는 것이 있으면 진행 전에 보고한다:
   - 프롬프트의 대조 요약과 인계장 내용이 다르다 → 어느 쪽이 맞는지 확인 요청
   - tickets.json의 `updated_at`이 인계장 생성 시각 이후다 → 그 사이 변경(보드 직접 저장 등)이 있었다 — 차이를 먼저 보고
   - 인계장 상태가 이미 "소비됨"이다 → 이중 재개 — 경고하고 사용자 확인 후에만 진행
   - 생성일이 오늘이 아니다 → 경고 1줄 (재개는 가능. 그 사이 /tp:done을 했다면 인계장은 이미 흡수·소비됐을 것이다)
3. **재개 브리핑**: 하던 일(체크리스트) · 미반영 결정 · 대기 질문 · 다음 행동을 표나 목록으로 보고하고, 어떤 것부터 할지 사용자 확인을 받는다.
4. 확인 후: 인계장 상단 상태를 `소비됨 (재개: {시각})`으로 바꿔 저장하고, 다음 행동을 진행한다. **쓰기 직전 파일을 다시 읽는다** — 1단계 이후 다른 세션이 이미 소비 처리했으면 이중 재개다. 덮어쓰지 말고 경고한 뒤 사용자 확인을 받는다. 저장했으면 저널에 `{"op":"write","file":"HANDOFF.md","note":"소비 — 재개"}` 1줄을 남긴다.
   - in_progress 티켓의 재개는 **ticket-run 프로토콜을 그대로** 따른다 (이미 완료된 단계를 파일 상태로 재확인, 같은 변경을 두 번 가하지 않음). 인계장은 정보지 증명이 아니다.
   - "미반영 결정"은 해당 티켓의 comments 기록이나 티켓 수정으로 먼저 반영할지 사용자에게 확인한다.

## 완료 기준

정리 모드:
- [ ] HANDOFF.md가 템플릿 형식으로 저장되었고 상태가 "대기"다
- [ ] tickets.json·메모리·프로필·CLAUDE.md를 수정하지 않았다
- [ ] 재개 프롬프트가 코드블록으로 제공되었다 (포인터 + 대조 요약)
- [ ] 커밋 안 된 변경이 있으면 커밋 제안이 보고에 있다

재개 모드:
- [ ] 정합성 검증 4항목(요약 대조·파일 변경·이중 소비·날짜)이 수행되었다
- [ ] 재개 브리핑 후 사용자 확인을 받았고, 인계장이 "소비됨"으로 마킹되었다
