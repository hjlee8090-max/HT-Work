# release-notes

## 목적
완료된 작업을 개발자 로그가 아니라 **사용자가 읽을 변경 안내**로 바꾼다.
`.ticket-pilot/tickets.json`의 `status: "done"` 티켓을 모아 버전 단위로 묶고,
사용자 언어로 다듬어 `RELEASES.md`에 최신 버전이 위로 오도록 기록한다.

## 입력
- `.ticket-pilot/tickets.json` — 티켓 원본. `status`, `title`, `purpose`, `result.summary`,
  `result.files_changed`, `result.followups`를 사용한다.
- (선택) 사용자가 지정한 버전 문자열(예: `v0.2.0`, `2026-07-23`). 없으면 3단계에서 제안한다.
- (선택) 기존 `RELEASES.md` — 이미 노트에 실린 티켓은 다시 싣지 않기 위한 대조용.

## 실행 단계
1. `tickets.json`을 읽어 `status == "done"` 티켓만 고른다. done이 하나도 없으면
   "릴리즈 노트로 낼 완료 티켓이 없다"고 알리고 종료한다.
2. `RELEASES.md`가 있으면 읽어, 이미 실린 티켓 ID를 수집한다. 이번 대상 = (done 티켓) − (이미 실린 티켓).
   새로 낼 티켓이 없으면 그 사실을 알리고 종료한다(중복 생성 금지).
3. 버전을 정한다. 사용자가 버전을 줬으면 그대로 쓴다. 없으면 이번 대상 티켓의 성격으로
   버전 후보 하나를 제안하고(예: 기능 추가면 마이너 올림 `v0.2.0`) 확인을 받는다.
4. 각 티켓을 사용자용 한 줄로 변환한다. 규칙:
   - `title`/`purpose`가 아니라 **사용자가 얻는 변화**를 쓴다. 예: "회원가입 폼 화면(UI) 추가" →
     "이제 이메일과 비밀번호로 회원가입할 수 있습니다."
   - 개발 용어(localStorage, submit 핸들러, DOM 등)는 사용자 언어로 바꾸거나
     처음 나올 때 한 줄로 풀어 쓴다(CLAUDE.md 소통 규칙 C-01). 파일명·함수명은 노트에 넣지 않는다.
   - `result.summary`의 동작을 근거로 삼되, 내부 구현 세부는 뺀다.
   - 성공 기준(SC-x)에 대응하면 괄호로 가볍게 표기해도 된다(예: "(회원가입 동작)").
5. 티켓을 성격별로 묶는다: `추가된 기능` / `개선` / `수정`. 판단이 애매하면 `추가된 기능`에 둔다.
   비고가 필요한 항목(예: `followups`에 사용자가 알아야 할 제한이 있으면)은 `참고`로 덧붙인다.
6. 아래 형식으로 이번 버전 블록을 만들어 `RELEASES.md` **맨 위**에 넣는다(기존 내용 보존).
   파일이 없으면 제목(`# 릴리즈 노트`)과 함께 새로 만든다.
7. 결론 → 근거 → 세부 순서로 사용자에게 보고한다: 어떤 버전에 티켓 몇 건을 실었는지(결론),
   대상 티켓 ID(근거), 저장 위치와 참고 항목(세부). **표 형식으로 정리하지 않는다**
   (소통 규칙 C-02는 2026-07-23 거부됨 — profile.md 거부 규칙 참조).

## 출력 형식
```markdown
## <버전> — <YYYY-MM-DD>

### 추가된 기능
- <사용자용 한 줄>  <!-- 근거: T-00x -->

### 개선
- <사용자용 한 줄>  <!-- 근거: T-00x -->

### 수정
- <사용자용 한 줄>  <!-- 근거: T-00x -->

### 참고
- <사용자가 알아야 할 제한·주의. 없으면 이 섹션 생략> <!-- 근거: T-00x followups -->
```
- 비어 있는 성격 섹션(추가된 기능/개선/수정)은 뺀다.
- `<!-- 근거: T-00x -->` 주석은 추적용으로 남긴다. 사용자에게 보이는 본문 문장에는 티켓 ID를 넣지 않는다.
- 날짜는 세션의 현재 날짜(currentDate)를 쓴다.

## 완료 기준(검증 방법)
- `RELEASES.md`가 존재하고, 맨 위 블록의 버전·날짜가 이번 실행 값과 일치한다.
- 이번 대상 done 티켓이 빠짐없이 한 줄씩 실려 있다(티켓 수 = 노트 항목 수).
- 각 항목이 파일명·함수명·내부 API 없이 사용자 언어로 쓰였다.
- 이미 이전 버전에 실린 티켓이 다시 실리지 않았다.
- 보고가 결론→근거→세부 순서이고, 표를 쓰지 않았다.

## 하지 않는 것
- 티켓 상태를 바꾸지 않는다(릴리즈 노트는 읽기 전용 집계다).
- `draft`/`suggested`/`rejected` 티켓은 싣지 않는다. `done`만 대상이다.
- git 커밋을 하지 않는다(프로필 규칙 R-03).
